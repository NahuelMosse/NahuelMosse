# UI patterns: when to choose each component

**When it is read:** when the visual brief picks a component for a screen (a button, a field,
a selection control, an overlay, a message, a collection, a loading state), and by the `judge` (lens `visual`) when it
judges the choice. **How:** only the sheet of the pattern the card touches, with `Read` and a line range of its
heading; never whole. `card.md` names the rule IDs that apply, and the `builder` receives those IDs and
their ranges. `reference/components.md` says what component of the catalog exists and links each row to its
sheet here; `reference/component-techniques.md` and `reference/modern-interface.md` say how it is built and
with which values; this reference says **when it is chosen**: what it is for, when not and what goes in its
place, how it is worded, how it behaves and how a reviewer or a test checks that the choice was right.
Accessibility is not repeated: it is cited by ID from `reference/accessibility.md` (A11Y-*). **Libraries and
design systems are options, not obligations.** **[NV] marks guidance not verified**: a hypothesis, never the
only evidence of a `meets`. How each rule is checked: `T` an automated test, `J` judgment with written
evidence, `C` a grep over the code. Source numbers `Bn` are in Sources. Where two sources disagree, the sheet
says which wins in the kit and why (the six clashes of the end are decided).

## 1. Actions and fields

### UX-BOTON — Button, hierarchy and link versus button

**Use when:** the action happens on the current page (send, save, open a dialog, delete); navigating to another URL is a link (B2, B3, B5). **Not when → instead:** it goes to another page or anchor → `<a href>`, even if styled as a button (GOV.UK's start button is a link); more than 2–3 actions of the same level → an actions menu or a split button. **Copy:** verb + object, in the repo's language and sentence case (“Create invoice”, not “Invoice” or “OK”); in a dialog the primary repeats the title's verb; do not truncate the label, wrap it to two lines (B2, B3). **Behavior:** responds on pointer-down; states rest → hover → focus → pressed → loading → success/error (disabled only if unavoidable); during loading it keeps its width and label and **does not submit twice** (`prevent-double-click` plus server protection, B5). **Accessibility:** A11Y-SEM-01, SEM-02, SEM-03, KBD-03, RSP-04; detectors A11Y-IA-01, IA-02, IA-06. **AI anti-patterns:** two or three accent-filled buttons in the same toolbar; a `div onClick` or `<a href="#">` as a button; generic “Send/OK/Accept”; every destructive button solid red, even a “Clear filter”; a disabled button with no explanation instead of validating. **In the set:** the button of `components.js` (spring press, loading with label, success morph, danger-tone error), `@shadcn/button`, `@aceternity/stateful-button`. **Sources:** B1 all buttons, B2, B3, B5, B7 alerts, B9 destructive actions.

**UX-BOTON-1** — One primary button per view; the header, a modal and a side panel have their own and do not count for the page; the secondary is the primary's alternative (Cancel, Back), the tertiary/ghost is for optional actions. · How T · criterion I18 · Check: per view `count(button[data-variant=primary]:visible outside dialog/aside) <= 1`; the loading button keeps `getBoundingClientRect().width` and a second click does not generate a second request · Source B1, B2, B3, B5.

**UX-BOTON-2** — The label is verb + object (“Create invoice”); short accepted exceptions: Cancel, Close, Delete. · How J · criterion none · Check: review of the diff's labels · Source B2, B3, B7.

**UX-BOTON-3** — The danger style only when the action is serious and not easily undone (GOV.UK's warning button, Pajamas' high severity); low severity (undoable, no loss) is a default button without red (Pajamas). Apple: inside an alert the destructive style goes only if the destructive action is **not** the one the user chose (a confirmed “Empty trash” is not painted destructive). The kit's “destructive is neutral with danger text until hovered” is compatible. · How J · criterion none · Check: review · Source B5, B7, B9.

**UX-BOTON-4** — Avoid disabled buttons: they do not explain why, they leave the tab order and have low contrast (GOV.UK, Atlassian). Better: an active button plus a validation that says what is missing; if disabling is unavoidable, see UX-AYUDA. · How J · criterion I16 · Check: no `disabled` button without its reason visible beside it · Source B3, B5.

### UX-INPUT — Text field and validation

**Use when:** the datum is open, or typing it is faster than choosing it: a name, an amount, a known country, a year, a remembered date (B10 dropdown list, date input). **Not when → instead:** a closed small set → radio/segmented (UX-SELECCION); an approximate value in a range → slider with an input beside it (UX-SLIDER). **Copy:** a visible label above; the expected format in the hint **before** the field; the placeholder is not a label (A11Y-FRM-01, FRM-06). Error messages follow GOV.UK's template by type: empty → an instruction (“Enter the tax id”); too long → a description (“The name must be 35 characters or fewer”); format → “Enter the tax id in the format 20-12345678-9”; no “invalid”, “please”, “oops” nor blame (“you forgot”); the same text in the field and in the summary. Accept tolerant formats: separators, month names, spaces (GOV.UK date input; “Forgiving Format”, B14). **Behavior:** success inline only on complex fields (available username, password strength); do not erase what was typed when showing errors (B5, B10). **Accessibility:** A11Y-FRM-01 to FRM-08, SEM-04, SR-01, AUT-01. **AI anti-patterns:** a red error as soon as the field is focused or while typing the first character; “Required field” / “Invalid value” generic; an error only in a toast or in a tooltip over an icon (NN/g: no tooltips for errors); `type="number"` for an ID number or tax id; a placeholder as the only label. **In the set:** the field of `components.js` (counter, animated error), `@coss/field`, `@coss/form`, `@coss/number-field`, `@coss/otp-field`. **Sources:** B5 error message and validation, B10 form errors, error messages, date input; B4 alerts.

**UX-INPUT-1** — Validate when the person tries to advance (submit, continue), as GOV.UK does; never mark “required” on leaving an empty field; after the first error, the field with the error is re-validated while it is corrected, and the message goes away as soon as it is corrected. On submit, every error is shown next to the field **and** in the summary with focus. Inline success only on complex fields. (NN/g validates when the field is finished and Shopify on leaving it; the kit follows GOV.UK, whose evidence is with users of public services, and `reference/modern-interface.md` and A11Y-FRM-05 say the same.) · How T · criterion I22 · Check: focus an empty required field and leave with Tab: no `[aria-invalid=true]`; submit with errors: focus is on the summary, `document.title` starts with “Error:”, each error has a link to the field and the typed value stays; correct the value: the message disappears without submitting again · Source B5, B10.

### UX-SELECCION — Select versus radio versus combobox versus segmented

Choose **one**: 2 options in a form → radio (Carbon: a dropdown with 2 → radio); 2–5 short options that change a **view** or an immediate parameter → segmented / content switcher; fewer than 5 form options → vertical radios; about 5–15 options, a secondary field, little space and a sensible default → select; 15 or more, or a known list (country, province, customer) → combobox with typing; having to see all to decide (filters) → a visible list of checkboxes/radios or a listbox; a value the user knows (a year, a quantity) → input (B1, B2, B10 dropdown list, listbox, drop-down menus). **Not when → instead:** a select in a public service for questions: GOV.UK treats it as a **last resort** on evidence (users do not close it, try to type, confuse the highlight with the choice, do not see it scrolls) → radios, or ask first to narrow; segmented as an on/off control → switch or checkbox; segmented with more than 5 options → select or chips; a select to navigate between pages → navigation; chained selects whose options change by another → ask in steps. **Copy:** radios with the question's label in a `<legend>`, options in a logical or alphabetical order (GOV.UK warns that ordering by frequency can reinforce bias), a “None” / “Don't know” option when valid; segmented labels short and of the same type; in a combobox, if creating is allowed the option is explicit (`Create "X"`), never a silent free value. **Behavior:** segmented and view radios apply at once, form radios on submit; unavailable options disabled with a reason, not hidden (NN/g); in a select the choice is distinguishable from the highlight. **Accessibility:** A11Y-FRM-07, APG-01, APG-05, SEM-01, SR-03. **AI anti-patterns:** a select of 2 or 3 options (“Yes/No”, “Monthly/Yearly”); a combobox for 4 states; a select of 200 countries without search; a segmented with 7 segments that wraps; tabs used as a table filter; a preselected radio on “Are you a registered taxpayer?”. **In the set:** select (listbox, Radix grammar), combobox (value = option or “Create X”), segmented (elevated thumb), radio; `@coss/select`, `@coss/combobox`, `@coss/autocomplete`. **Sources:** B1 segmented, B2 dropdown and content switcher, B5 radios and select, B10.

**UX-SELECCION-1** — The default of a radio group: in **settings** (there is a current value) one is always selected; in **questions about the person's data or decisions with consequences** (what the user declares) none is preselected (GOV.UK); a preselected radio is fine where a safe default exists (NN/g: preselect in most cases). · How J · criterion none · Check: review of each radio group of the diff against the two cases; a DOM inventory test: every `<select>`/`[role=listbox]` of a form has 5 or more options or a justification in the plan, every segmented has 2–5 segments · Source B5, B10.

### UX-CHECK-SWITCH — Checkbox versus switch

**Use when:** a **switch** for a binary preference that **applies on the spot**, with no Save button (NN/g, Carbon, Fluent); a **checkbox** for a binary option applied on submit, multiple selection, consent, or an indeterminate state. **Not when → instead:** a switch inside a form that has “Save” → checkbox (the user does not know whether it applied); a switch for an action that needs confirmation (delete) → button; more than two states → radio or segmented; a checkbox that triggers an action (“Show details” that opens a panel) → button or disclosure; on iOS, a switch only in list rows (B7). **Copy:** the switch's label is the setting, starting with the keyword, in the positive (“Email notifications”, not “Do you want to receive…?” nor “Disable…”); NN/g's test: read it with “yes/no” at the end; a checkbox label in the positive, with no negations; a consent checkbox never pre-checked. **Behavior:** the switch shows the result and, if the change goes to the server, a pending state and a reversal if it fails (optimistic UI, Pajamas). **Accessibility:** A11Y-SR-03 (`role=switch`/`aria-checked`), FRM-07, COL-02, COL-03, RSP-04. **AI anti-patterns:** a settings page with switches **and** a “Save changes” button at the bottom; a switch for “I accept the terms”; a switch with no label beside it and the state only in color. **In the set:** a switch that fills from the knob, a checkbox with a ring, `@coss` checkbox/switch. **Sources:** B10 toggle and checkboxes vs radio, B2 toggle, B6 switch, B7 toggles, B9 saving.

**UX-CHECK-SWITCH-1** — A switch applies its change at once and never lives in a form or container with a submit button. · How T · criterion I21 · Check: **“never a switch that requires Save”**: in each `form` or container with a submit button `count([role=switch]) == 0`; toggling a switch produces a request (or a persisted state change) with no other click; after reloading, the switch keeps its value · Source B10, B2, B6.

### UX-SLIDER — Slider

**Use when:** the approximate value is enough and the user explores (a price, a volume, a filter range) (NN/g). **Not when → instead:** the exact value matters (an age, an amount, a tax percentage) → a numeric input; a wide or dense range that demands fine precision → input or stepper. **Copy:** label and current value visible above or beside, not below (the thumb covers them); unit and ends written. **Behavior:** keys: arrows, PageUp/Down, Home/End. **Accessibility:** A11Y-APG-07, APG-01, RSP-04, SR-03 (a readable `aria-valuetext`: “$ 12,000”). **AI anti-patterns:** a slider for an invoice amount; a slider with no visible value; the value bubble below the thumb on mobile. **In the set:** a slider with a leaning bubble (`components.js`). **Sources:** B10 slider; B15 2.5.7.

**UX-SLIDER-1** — A slider always has a way without dragging: a click on the track moves the thumb (WCAG 2.5.7) and, if the value matters, a synchronized input. · How T · criterion I14 · Check: a click on a point of the track changes the value; arrows change it; the value is announced with a formatted `aria-valuetext` · Source B15.

### UX-FECHA — Date picker versus date input

**Use when:** a **calendar** for near dates (about a year at most), ranges (trips, report periods) and when the day of the week matters; a **typed input** (one or three fields) for dates the user knows or can look up (birth, expiry of a document) (GOV.UK, NN/g, M3). **Not when → instead:** a modal calendar for far dates → input (M3: not the modal picker for a birth date); three day/month/year dropdowns → input (more clicks); few valid dates (about 10 or fewer) → a list of options. **Copy:** the format in the hint (“For example, 27 3 2026”); accept month names (GOV.UK: errors dropped); avoid an ambiguous `10/11/2026`: show the month in letters in the confirmation; named range shortcuts (“This month”, “Last 30 days”). **Behavior:** a docked picker offers typing **and** choosing at once (M3); ranges: forbid an end before the start and disable the illogical; **never move focus by itself** between day, month and year (GOV.UK). **Accessibility:** A11Y-FRM-07, FRM-08, FRM-02 (`bday-*`), APG-01. **AI anti-patterns:** a calendar as the only way to enter a birth date; focus auto-advance between fields; a `MM/DD` format in a Spanish-language app. **Check:** typing “27/3/2026”, “27-03-2026” and “27 March 2026” gives the same date; the calendar is walked with arrows and Enter picks. **In the set:** a keyboard-navigable date picker, ranges, a common footer (today, this week, this month, last 30 days, clear); `@coss/calendar`. **Sources:** B1 date pickers, B5 date input, B10 date input.

## 2. Overlays and messages

### UX-OVERLAY — Modal/dialog versus drawer/sheet versus popover versus a new page

| Need | Pattern | Source |
|---|---|---|
| A critical decision or a datum that blocks the flow the user started; a short, infrequent task | **modal** | B1, B2, B10 |
| See or edit the detail **without losing the list** behind; compare with what is behind | **drawer / non-modal side panel** or split view | B10 data tables, B6 |
| Little information or 1–3 actions related to an element, dismissible | **popover** | B7 |
| A complex flow, many decisions, large tables, or the decision needs information the modal covers | **new page** | B2, B3, B10 |
| Mobile, content that does not fit a popover | **sheet** | B7 popovers |

**Not when → instead:** a modal for repeated tasks (Carbon) → inline; a modal for information with no action (Apple, Fluent) → a toast or inline message; a modal to show errors (Shopify) → inline / banner; an onboarding or promotion modal on load (NN/g popups, Apple) → contextual; a popover for a warning (Apple: it is lost or closed by accident) → an alert; a popover with a long form → drawer or page. **Copy:** a title that names the specific task or question; no “Are you sure?”, “Attention!” nor apologies (M3, Apple); at most two actions (M3) or three (Fluent, Apple); no “More information” that takes the user out of the dialog; the primary is the title's verb. **Behavior:** validate before closing and leave the modal open with the error inline (Carbon); fixed header and footer, the body scrolls, never horizontally (Carbon, Fluent). **Accessibility:** A11Y-KBD-07, KBD-08, SR-04, APG-06; detector A11Y-IA-08; the alert dialog has no close on outside click, Cancel first and with focus (`reference/component-techniques.md`). **AI anti-patterns:** every “Edit” opens a modal, even that of a 30-column table; a confirmation modal that opens a second success modal; a 6-step wizard inside a modal; a popover with 8 fields and Save; a “Welcome!” modal on first login. **In the set:** `overlays.js` (dialog and drawer with header/body/footer; popover; hover card), a card → dialog morph (`motion/morphing-dialog`), a detail split-view panel (J/K, hash), `motion/morphing-popover`, `@coss/dialog`, `@coss/alert-dialog`, `@coss/drawer`, `@coss/sheet`, `@coss/popover`. **Sources:** B1 dialogs, B2 modal, B3 modal, B4 alerts, B6 dialog, B7 popovers, modality, alerts, B10 modal-nonmodal, popups, data tables.

**UX-OVERLAY-1** — A modal does not open another modal (Atlassian, Fluent, Apple, NN/g popups). The exceptions the sources admit: a “Discard changes?” alert over a full-screen dialog or sheet (M3, Apple), listed in the plan. · How T · criterion I19 · Check: **“a modal does not open another”**: with a `dialog[open]`/`[role=dialog][aria-modal=true]` visible, run each of the modal's actions and assert `count(visible modals) <= 1` (except the listed discard alert) · Source B3, B6, B7, B10.

**UX-OVERLAY-2** — One popover at a time, never in cascade; opening another closes the previous one with a single click (Apple). A non-modal popover closed by an outside click **saves** what was done; only Cancel discards (UX-OVERLAY-3, Apple). · How T · criterion I19 · Check: with a popover open, opening another leaves `count([data-state=open][role=dialog]:not([aria-modal])) == 1` · Source B7.

**UX-OVERLAY-3** — Closing a modal or drawer with unsaved content asks for confirmation (Apple, M3, Pajamas). · How T · criterion none · Check: editing in a drawer and closing with Esc shows the discard confirmation · Source B7, B1, B9.

### UX-CONFIRMAR — Confirmation versus undo

**Use when:** **undo** is the default option where it is feasible: the action is common and reversible, even if destructive (Apple: no alert on deleting an email; NN/g: prefer undo where possible); **confirmation** for a serious, irreversible consequence, or with money (NN/g, Apple, Carbon's danger modal); **confirmation by typing the name** to delete something that drags related resources (a project, an account) (Pajamas; NN/g: keep it for rare cases, if it becomes frequent it is automated). **Not when → instead:** confirming routine actions → undo (it trains clicking without reading); a generic “Are you sure?” → a specific one. **Copy:** name what is affected (“Delete invoice 1042 of Acme?”; with several, list them or name the first); buttons with the result (“Delete invoice” / “Keep”), never Yes/No; say what is lost and whether there is a recovery period. **Behavior:** no default “Yes”; initial focus on Cancel in the alert dialog; undo: the row leaves at once, the toast offers Undo, and if the request fails it comes back with the error (`reference/modern-interface.md`). **Accessibility:** A11Y-FRM-11, APG-08 (Undo reachable by keyboard), KBD-08. **AI anti-patterns:** a confirmation dialog on every deletion of a draft row; “Are you sure?” with Yes/No and the Delete button focused; an Undo that exists only in a 4 s toast. **In the set:** the toasts' undo bar, `@coss/alert-dialog`. **Sources:** B10 confirmation dialog, B7 alerts, B9 destructive actions, B2 modal.

**UX-CONFIRMAR-1** — A reversible deletion, where undo is feasible, opens no dialog and shows Undo; Undo restores the item in its position. · How T · criterion I24 · Check: delete a reversible item: no dialog, the Undo is visible, and restores it in place · Source B7, B10.

**UX-CONFIRMAR-2** — An irreversible action has a specific confirmation that names what is affected, with buttons that say the result and initial focus on Cancel. · How T · criterion I24 · Check: in the alert dialog `document.activeElement` is Cancel and Enter does not delete; the plan's list of irreversible actions has each one with its confirmation · Source B10, B7.

### UX-FEEDBACK — Toast versus banner versus inline alert

| Message | Pattern | Persistence | Source |
|---|---|---|---|
| A brief confirmation of a user action that does not show itself (“Invoice sent”) | **toast** | goes by itself (about 4 s; 4–7 s in the sources), pauses on hover/focus | B1, B2, B6, B8, B9 |
| An error of a field | **inline** next to the field + summary | until corrected | B5, B10 |
| An error or notice of a section or of a failed action | **inline / section message** above the element | until resolved | B3, B4 |
| A state of the system or the account that affects the whole app (offline, expired subscription) | **banner** | until it stops applying | B3, B4, B2 |
| Something that happened elsewhere or ends later (an export is ready, a mention) | **notification** + center (UX-NOTIF) | until read | B2, B9 |
| Critical, demands a decision now | **modal** | blocks | B2, B6 |

**Not when → instead:** a toast for errors the user has to see → inline or banner (NN/g: the user waited 5 minutes; Shopify; Fluent), the exception being persistent connection errors; a toast when the change is already visible (the row changed state) or when creating already takes to the record (Pajamas, Salesforce); a toast that needs to survive a navigation or reload → an alert/banner; more than one banner at a time → combine or show the one of highest priority; a banner plus an error summary in the same view → only the summary. **Copy:** a toast is short (Shopify 3 words or fewer; Fluent about 60 characters of body); confirmations in participle (“Invoice sent”), progress in gerund (“Uploading file”); no final period in titles; no decorative icons nor inline links (M3); an error says what happened + what to do, no blame or humor; severity with text or an icon with a name, not color alone (A11Y-COL-03). **Behavior:** the focus does **not** move to the toast (Salesforce); stacking: M3 says one at a time, Fluent at most 4, Carbon and Atlassian stack with the newest on top, the set stacks 3 visible; in the web a toast that dismisses itself has an equivalent feedback in the place of the action (a “Saved ✓” button). **Accessibility:** A11Y-SR-01, SR-02, APG-08, COL-03, FRM-03, FRM-04; detector A11Y-IA-09. **AI anti-patterns:** a toast for everything, “Filter applied” and validation errors included; a red error toast that goes away at 3 s; three banners stacked at the top; an `aria-live` region created together with the message (not announced). **In the set:** stacked toasts with swipe and an undo bar, `ui.toast.promise`, a check that draws itself (`overlays.js`, `life.js`); `@coss/toast`. **Sources:** B1 snackbar, B2 notification, B3 flag, banner, section message, B4, B5, B6, B8, B9, B10.

**UX-FEEDBACK-1** — A toast is not used for errors the user has to see: they go inline or in a banner. · How J · criterion none · Check: an inventory of the card's messages against the table above · Source B10, B4, B6.

**UX-FEEDBACK-2** — A toast **with an action** (Undo) stays until the person interacts or at least 10 s of effective visibility, pauses on hover, on focus and with a hidden tab, and its action **also exists outside the toast** (a `Ctrl+Z` shortcut or the restorable item in its place). Informational toasts with no action stay at about 4 s. (M3: the snackbar with an action stays until acted upon; Carbon: an actionable one persists; Salesforce: dismissible 4.8 s without a link, **9.6 s with a link**; Pajamas advises against actions in toasts. The set's 4000 ms toast with an Undo inside is corrected.) · How T · criterion I20 · Check: **“a toast with an action lasts 10 s or more or until interaction”**: trigger the action, wait 9 s (fake clock) and the toast is still there; with a hover at second 3, at 15 s it is still there; the undo is reachable with `Ctrl+Z` or in the item's place · Source B1, B2, B8, B9, B6.

**UX-FEEDBACK-3** — Error toasts are not dismissed by themselves (Atlassian, Carbon). · How T · criterion I20 · Check: an error toast is still visible at 30 s; the `role=status`/`role=alert` region exists on load, before any message · Source B3, B2.

### UX-AYUDA — Tooltip versus popover (toggletip) versus help text

**Use when:** a **tooltip** for the name of an icon button, or a brief and **non-essential** clarification of a control (NN/g, Carbon, Fluent); a **toggletip / popover on click** for help with formatting, links or buttons, or the explanation of a term (Carbon); a **visible help text (hint)** for everything the user needs to complete the task (password requirements, format). **Not when → instead:** vital information → a visible hint; interactive content in a tooltip → a toggletip; system feedback or errors in a tooltip → inline; news announcements as a tooltip → another pattern; touch has no hover → toggletip or hint. **A tooltip on a disabled button:** the sources clash (Atlassian: never; Fluent: yes, to explain how to enable it). The kit decides: avoid `disabled` when the reason has to be explained; use `aria-disabled="true"` (so it stays focusable) with the reason visible beside the button or in a tooltip reachable by keyboard; **never a tooltip over a real `disabled`** (it receives neither focus nor hover on every browser). **Copy:** brief, self-sufficient, **it does not repeat the label**; no final period for a noun phrase (Fluent). **Behavior:** hover **and** focus; Esc closes; the pointer can be moved over it (A11Y-APG-06); it opens after intent (the kit: 400 ms; Radix 700 ms) and at once while “warm”; consistent: if one icon of the toolbar has a tooltip, all do; it does not cover what it describes. **Accessibility:** A11Y-APG-06, SEM-02, SEM-04; detector A11Y-IA-12. **AI anti-patterns:** an “i” icon with a tooltip that holds the only datum explaining a required field; a tooltip that repeats the button's text; links inside a tooltip; a tooltip as the accessible name (`title`) of an icon button. **Check:** each tooltip opens with keyboard focus and closes with Esc, and the icon button has an accessible name without the tooltip; a grep of `<Tooltip` with `<a`/`<button` inside fails; review: is the content essential? → a visible hint. **In the set:** a “warm” tooltip that slides to the next anchor, a hover card, `@coss/tooltip`, `@coss/popover`; `motion/animated-tooltip`. **Sources:** B10 tooltips, B2 tooltip, B6 tooltip, B3 button (disabled).

### UX-MENU — Actions menu and context menu

**Use when:** secondary actions of an element that do not fit as buttons (⋯ on a row); a context menu (right click / long press) as a **shortcut** for experts (NN/g). **Not when → instead:** the action is the main or a frequent one → a visible button; site navigation → a list of links with disclosure, not `role=menu` (A11Y-APG-03). **Copy:** 10–12 items at most, by frequency, rare ones below, complete groups (Cut/Copy/Paste); verb + object; destructive at the end and separated; unavailable items disabled, not hidden; the trigger is ⋯ or a caret, not a gear or a hamburger. **Behavior:** no submenus in context menus; in app menus, a submenu by click or with a grace polygon; navigation submenus by click, not by hover. **Accessibility:** A11Y-APG-03, KBD-01, SR-03; detector A11Y-IA-12. **AI anti-patterns:** `role=menu` on the nav; “Delete” as the only way in a right click; a menu of 20 items with 3 levels. **Check:** the menu opens with Enter/Space, arrows walk it, Esc returns the focus. **In the set:** a floating surface for menus (icons, checkbox/radio items, submenus, context menu, accelerators; a highlight pill), `motion/profile-dropdown`, `@coss/menu`, `@coss/context-menu`. **Sources:** B10 contextual menus, menu design.

**UX-MENU-1** — An action that exists only in the context menu is also visible somewhere else (NN/g). · How T · criterion none · Check: each `menuitem` of a context menu has an accessible equivalent outside it (an inventory in the plan) · Source B10.

### UX-PALETA — Command palette

**Use when:** a product with many actions and frequent users, with the keyboard as the fast path (`reference/modern-interface.md`). **Not when → instead:** as the only path to an action → there is always a visible path (a button, a menu); on touch without a keyboard → a visible search button. **Copy:** each command shows its shortcut beside it (the palette teaches shortcuts); synonyms (“cancel” finds “Issue credit note”). **Behavior:** the same shortcut across the app (⌘K / Ctrl+K), without clashing with typing; fuzzy matching and ranking by context; recents on top; an empty state with a suggestion; no life beyond feedback. **Accessibility:** A11Y-APG-05 (focus in the input, `aria-activedescendant`), KBD-09. **AI anti-patterns:** a palette that opens with expressive animation; actions only in the palette; a shortcut that overrides `Ctrl+F` or fires when typing in an input. **Check:** `Ctrl+K` opens from each route; with focus in a text `input` a bare letter fires no shortcut. **In the set:** a palette that searches invoices and customers (recents, subpages, shortcuts), `@coss/command`, `motion/action-search-bar`. **Sources:** B16 (NN/g has no article on palettes).

**UX-PALETA-1** — The palette is never the only way to an action: each command has a visible equivalent (an inventory in the plan). · How T · criterion none · Check: the inventory · Source B16 [opinion of practice, not a study].

## 3. Navigation and sections

### UX-SECCIONES — Tabs versus segmented versus accordion

**Use when:** **tabs** for distinct sections of the same object with short labels, the first one the most relevant, with no need to compare between them, frequent users (GOV.UK, NN/g); **segmented / content switcher** for alternative views **of the same content** (list / board / timeline; day / week / month) (Carbon, M3); an **accordion** for many loosely related sections of which the user needs few, mobile, FAQ, several open at once (NN/g, GOV.UK). **Not when → instead:** comparing between tabs, or reading all in order → one page with headings; the critical in a non-visible tab → show it on top; long labels or more tabs than fit in a row → a side menu or page (a single row); an accordion for content everybody needs, or to split a series of questions; nesting tabs in accordions or the reverse; tabs as navigation between pages (GOV.UK: not page navigation) → nav. **Copy:** tabs 1–2 words, plain language, no sustained capitals; accordion headings descriptive because hidden content is overlooked. **Behavior:** automatic activation only if the panel appears without delay (A11Y-APG-04); the tab's state goes in the URL if the view is shared; each accordion section keeps its state and is searchable with Ctrl+F. **Evidence:** GOV.UK states its tabs component was **not tested with users**. **Accessibility:** A11Y-APG-02, APG-04. **AI anti-patterns:** tabs with 9 tabs that scroll horizontally; settings of 3 fields spread over 4 tabs; tabs in capitals with wide tracking; an accordion for a “Tax data” section every user must review. **Check:** the tablist in a single row at 1280 px wide (no overflow) and walkable with arrows; reloading with `#tab=…` opens that tab; review: is there comparison between sections? does everybody need everything? **In the set:** tabs with a sliding pill (`motion/tabs`), segmented, accordion (`grid-template-rows`), `motion/smooth-tab`, `motion/transition-panel`. **Sources:** B5 tabs, accordion, B10 tabs, accordions, B2 content switcher, B1 segmented.

### UX-MIGAS — Breadcrumbs

**Use when:** a hierarchy of 3 or more levels; users arriving by link or search at a deep level (NN/g). **Not when → instead:** a flat or linear site (1–2 levels, a wizard) → title and “Back”; as a replacement of the main navigation; as a session history. **Copy:** it ends at the current page, without a link and distinct; links only to real pages; on mobile do not wrap: show only the last one or two levels. **Accessibility:** `nav aria-label="Path"`, `aria-current="page"` (A11Y-SR-03), SEM-05. **AI anti-patterns:** a breadcrumb “Home > Dashboard” in a one-level app; a clickable last item; categories with no page of their own as links. **Check:** the last item is not an `<a>` and has `aria-current="page"`; each `href` answers 200; review: depth 3 or more. **In the set:** the breadcrumb (dimmed links, the current one in the foreground). **Sources:** B10 breadcrumbs.

### UX-NAV — Side versus top navigation

**Use when:** **side (sidebar)** for applications, a broad or growing architecture, more than about 7 destinations (NN/g); **top** for sites with few first-level destinations that fit without shrinking or shortening; a **bottom bar** (mobile) for 3–5 destinations, **not on desktop** (M3). **Not when → instead:** a hamburger on desktop when there is room; icons without a label in the expanded nav (collapsed to icons → tooltips); navigation menus by hover. **Copy:** specific and known labels, keyword first, no marketing names. **Behavior:** the least used, below. **Accessibility:** A11Y-KBD-05, KBD-06, SR-03 (`aria-current`), APG-03, RSP-06. **AI anti-patterns:** a sidebar and a top bar with the same destinations; the current item with an accent bar + fill + bold + icon (the kit: one signal per state); 14 items without groups. **In the set:** a sidebar (16 rem, collapsible, Ctrl/⌘+B), `motion/animated-background` for the current page, `motion/floating-dock` (quick actions, not navigation). **Sources:** B10 vertical nav, menu design; B1 navigation bar.

**UX-NAV-1** — Where I am is always indicated (NN/g: the most common mistake). · How T · criterion none · Check: on each route exactly one item with `aria-current="page"`; review: the number of destinations and the foreseen growth · Source B10.

### UX-WIZARD — Form in steps versus one page

**Use when:** a **wizard** for a rare task or for novices, steps that depend on previous answers, many fields (NN/g; GOV.UK: “one thing per page” for public services); **one page** for a frequent task of experts, when comparing between sections is needed, few fields (NN/g: interaction cost; GOV.UK admits grouping in fast internal services **if research supports it**). **Not when → instead:** a wizard inside a modal (it covers information the process needs) → a page; a wizard for a 5-field form used 20 times a day → one page. **Copy:** steps with a short name; buttons with the next step's name or “Continue”, not “Next”; a “Review your answers” page with “Change” per section before submitting; the final button says the action (“Issue invoice”) (GOV.UK check answers). **Behavior:** going back (link and browser button) keeps what was loaded; save and resume; do not ask twice for the same (A11Y-FRM-09); a progress indicator: GOV.UK removed one from 12 steps with **no effect** on completion or time: test without it first. **Accessibility:** A11Y-FRM-04, FRM-09, KBD-06 (focus on each step's `h1`), AUT-05. **AI anti-patterns:** a 5-step stepper with one field per step in a back office; generic “Next / Previous”; going back erases what was loaded. **Check:** complete step 2, go back to 1 and advance: step 2 keeps its values; the browser's Back button returns to the previous step, it does not leave the flow; review: task frequency × number of fields. **In the set:** `motion/transition-panel` (invoice form in steps), `motion/ai-prompt` + `motion/file-upload`. **Sources:** B10 wizards, B5 question pages, check answers.

### UX-BUSQUEDA — Search and filters

**Use when:** a **visible search box** when the user knows what they look for (NN/g: a box, not a link; +91 % use); **filters** to narrow by attributes; **facets** when several filters describe the set. **Not when → instead:** search hidden behind an icon on desktop when it is the main task → a visible box; interactive filters on a slow connection or with users who know what they want → batch with “Apply”. **Copy:** a placeholder that says what is searched (“Search by customer, tax id or number”) with an accessible label; a count per facet to avoid empty combinations; active filters visible as removable chips and “Clear all”. **Behavior:** when in doubt, batch; interactive: dim the results and show progress; do not jump to the top while filtering; the state of search and filters in the URL. **Accessibility:** A11Y-SR-01 (“12 results”), SR-05, APG-05 (autocomplete). **AI anti-patterns:** a filter that jumps to the top on each checkbox; results recomputed while typing with no debounce; applied filters invisible after closing the panel. **Check:** apply filters and reload: same filters and results; the count is announced in an existing live region. **In the set:** `motion/toolbar-dynamic`, `motion/kokonut-toolbar`, the palette for global search. **Sources:** B10 search, applying filters, filters vs facets.

### UX-ARRASTRE — Drag and drop and its alternative

**Use when:** reordering, moving between columns (a board), resizing, when the user expects it and there is no cheaper way (NN/g). **Not when → instead:** as the only way; on mobile with long lists → a menu or cut/paste. **Behavior:** on picking up, a shadow, a ghost or a displacement; neighbors shift in about 100 ms with easing, the rearrangement fires when the object's **center** crosses the edge; drop zones a bit larger than the visible; the active zone highlighted; keyboard: pick up with Space, arrows, drop, Esc cancels, with announcements (A11Y-APG-07). **Accessibility:** A11Y-APG-07, KBD-01. **AI anti-patterns:** a kanban with no other way to change the state; a drag handle that looks like a hamburger menu with no label. **Check:** move a card between columns without `mouse.down/move` (by menu or keyboard) and with announcements in the live region; Esc during the drag returns it to the original position. **In the set:** `drag.js` (a real-size placeholder, neighbors with spring, autoscroll, Space, arrows and Esc). **Sources:** B10 drag-drop; B15 2.5.7.

**UX-ARRASTRE-1** — Drag is never the only way: there is always “Move to…”, up/down or a status select (WCAG 2.5.7 AA). · How T · criterion I14 · Check: the card changes column by menu or keyboard, with no pointer drag · Source B15, B10.

## 4. Collections and data

### UX-COLECCION — Table versus list versus cards

**Use when:** a **table** for homogeneous records with several attributes to **compare, sort, filter and act on in batch** (NN/g: four tasks); a **list** for homogeneous items to scan or look for one; **cards** for **heterogeneous** content to browse, each card an entry to its detail (on mobile the table becomes a two-line card, the kit). **Not when → instead:** cards for data that is compared (invoices, amounts) → a table; a table for 3 items with one attribute → a list; a `div` grid for tabular data → `<table>` (A11Y-TAB-01, IA-14). **Copy:** the first column a readable identifier; related columns together; numbers to the right with `tabular-nums`. **Behavior:** fixed header; a wide table has a fixed first column; limited row actions; batch with checkboxes and “Select all”; active filters visible; filtering does not change widths. **Accessibility:** A11Y-TAB-01 to TAB-04, RSP-01; detector A11Y-IA-14. **AI anti-patterns:** a dashboard of identical cards with one number each; a whole clickable row with buttons inside (A11Y-TAB-03); a 12-column table with no sort or filter. **Check:** tabular data is in `<table>` with `<th scope>`; sorting updates `aria-sort`; filtering changes no column width; review: does the user compare? → a table. **In the set:** a table with FLIP, selection, a selection bar, rows that enter and leave, a skeleton that respects columns, mobile cards (`data-cards="summary"`), `@coss/table`, `motion/expandable-card`, `motion/bento-grid`. **Sources:** B10 data tables, cards.

### UX-PAGINACION — Pagination versus infinite scroll versus “Load more”

**Use when:** **pagination** to look for, compare, go back to an item (“it was on page 3”), back-office tables; **“Load more”** for long lists where reaching the footer matters, mobile, slow connections; **infinite scroll** for homogeneous content to browse without a goal (feeds, activity). **Not when → instead:** infinite scroll on search results, tables or when there is a footer with links → pagination or “Load more”. **Copy:** “Showing 1–50 of 1,234”; “Load 50 more”. **Behavior:** the page goes in the URL; infinite scroll has a loading indicator so it does not look finished, and a reachable footer; after “Load more” focus goes to the first new item (A11Y-KBD-08). **Accessibility:** A11Y-SR-05, SR-01, KBD-08; `aria-current="page"`. **AI anti-patterns:** infinite scroll in the invoices table; pagination with no total; going back from the detail and landing on page 1. **Check:** go to page 3, open an item, go back: page 3 and the item in view; after “Load more” `activeElement` is the first new item and “50 more” was announced. **In the set:** pagination (36 px, the current with `aria-current`), `motion/animated-list` for recent activity. **Sources:** B10 infinite scrolling.

**UX-PAGINACION-1** — On returning from the detail, the position (page or scroll) is kept (NN/g). · How T · criterion none · Check: the test above · Source B10.

### UX-VACIO — Empty states

**Use when (three types):** **no data yet** (first use): what will appear, what it is for and the action that fills it; **the result of an action** (a search or filter with no results): say why and how to widen (“Remove filters”); **error / no permission / missing configuration**: why there is no data and what to do. **Copy:** a positive and concrete title; one main action; no jokes in errors; no dead end; a decorative illustration with `alt=""`; several empties at once: text or a tertiary button only. **Behavior:** it replaces the table and its headers (the kit uses a row with a message inside the table for filters: compatible if the header stays and the row says the reason and the action). **Accessibility:** A11Y-SR-01 (“No results” announced), SR-05, SEM-07. **AI anti-patterns:** a giant illustration and “Nothing here!” with no action; the same empty for first use and for a filter with no results; an empty that shows up 200 ms before the data. **Check:** with the API delayed 2 s the empty text is never seen before the response; a filter with no results shows a message with a working “Remove filters” action; review: each empty of the diff is of one of the three types and has an exit. **In the set:** the set's empty state, a first-use empty with life (words, dots, a pulse three times), `@coss/empty`. **Sources:** B2 empty states, B10 empty states.

**UX-VACIO-1** — While loading, a loading indicator is shown; never a “No records” that is contradicted afterwards (NN/g). · How T · criterion I23 · Check: with the API delayed 2 s the empty state never shows before the response · Source B10, B2.

### UX-CARGA — Skeleton versus spinner versus progress

| Wait | What to show |
|---|---|
| under about 0.4 s | nothing extra; the action's feedback (pressed) is enough (Doherty 400 ms; NN/g 0.1 s instantaneous) |
| about 0.4–1 s | nothing **or** an indicator with a delay that does not flash |
| 1–10 s | a **skeleton** if a page or region of known shape loads; a **spinner** if it is a module or a single action (a button in loading) |
| over 10 s | a **progress bar** with a percentage or “3 of 50”, an estimate and how to cancel |
| minutes | background work + a notification on finishing (Carbon) |

**Not when → instead:** a skeleton in menus, dropdowns, toasts or whole modals (Carbon) → an inline spinner; a “frame-display” skeleton (only header and background) → a skeleton with the real shape; a spinner for uploads, exports or conversions → progress; a static “Loading…” with no movement or progress. **Behavior:** progress that does not stall at the end; interactive filters: dim results with an indicator while recomputing. **Accessibility:** A11Y-SR-05 (announce start and end), MOV-01 (shimmer → fade), MOV-02. **AI anti-patterns:** a full-screen centered spinner to load a 20-row table; a generic three-bar skeleton that does not match the layout (a jump on arrival); a fake progress bar that reaches 99 % and stays. **Check:** a response at 100 ms shows no `[data-skeleton]`; at 2 s it appears and the columns match the data's in x (± 2 px); an export of over 10 s shows `role=progressbar` with `aria-valuenow`; CLS under 0.1 on replacing the skeleton. **In the set:** a skeleton with a shimmer band that respects columns, `motion/kk-loader`, `motion/animated-circular-progress-bar`, `@coss/skeleton`, `@coss/spinner`, `@coss/progress`, `@coss/meter`. **Sources:** B10 skeleton, progress, response times; B2 loading pattern; B11 Doherty.

**UX-CARGA-1** — The skeleton appears only after about 300 ms, so it does not flash, and once visible it stays a minimum of about 400 ms [NV: the minimum stay is the practice of libraries, not in the sources read]; under 1 s no indicator is required (NN/g). The kit's skeleton, which shows from 150–300 ms, does not contradict NN/g: both fit in this rule. · How T · criterion I23 · Check: a response at 100 ms shows no skeleton; a response at 2 s does · Source B10, B11.

### UX-ESTADO — Badges, tags and states

**Use when:** a **status label** (a pill with text) for the state of a record (Paid, Overdue, Draft); a **badge with a number or a dot** over an icon when there is news, cleared on acknowledging it (Carbon); a **differential indicator** (▲ ▼ +/−) for the change of a value (Carbon). **Not when → instead:** a state in color alone (a green dot) → color + shape/icon + text (Carbon: at least 2 of color, shape, symbol; 3:1); a badge with a number that cannot be “cleared” → a counter in the label; an accent pill for neutral states (the kit: the accent marks value and selection, not state). **Copy:** one term per state across the app; an adjective or participle (“Overdue”, not “To overdue”); a severity scale: high (needs action), medium, low (Carbon). **Behavior:** when consolidating states show the one of highest attention; a live state change is announced (A11Y-SR-01). **Accessibility:** A11Y-COL-02, COL-03, SR-03. **AI anti-patterns:** seven pill colors with no legend; a red “99+” badge on everything; a green “Active” state with no text on mobile. **Check:** each `[data-status]` has visible or accessible text besides the color; review: one glossary of states in the plan. **In the set:** a status that pings the first time it is seen, a badge that grows from its edge, a state change in place. **Sources:** B2 status indicator pattern, B10 indicators.

### UX-NOTIF — Notifications

**Use when:** events that are not an immediate answer to the user's action: finished background work, mentions, changes by others (Carbon “system-generated”, Pajamas, Fluent “communication”). **Not when → instead:** feedback on what the user just did → UX-FEEDBACK; information that cannot be lost in a passive notification → an action required or inline; notifications that do not serve the user's goal (they are ignored). **Behavior:** a notification center (a panel) the user opens; a badge with a dot or number cleared on reading; a toast may announce them but the content stays in the center; the user can manage or mute the non-critical; the critical ones do not go by a timer. **Accessibility:** A11Y-SR-02 (polite by default), KBD-09, MOV-02 (what auto-updates can be paused). **AI anti-patterns:** a toast for every system event; a permanent red badge; a notification with no destination to take to. **Check:** a system notification appears in the center and persists after a reload; the badge drops on opening it; review: each notification has a recipient and a destination. **In the set:** `motion/animated-list` (recent activity), toasts. **Sources:** B2 notification pattern, B6 toast, B9 toast, B10 indicators.

### UX-ONBOARDING — Onboarding

**Use when:** **contextual** (“pull”) help at the moment it is needed: an empty state that teaches, a hint beside the step, a reopenable “What's new” (NN/g onboarding, empty states); a guided tour only for unfamiliar paradigms. **Not when → instead:** a welcome carousel or a tour on first login → empty states that teach, sample data (Carbon “starter content”); a modal on opening the app (Apple, NN/g popups); explaining obvious conventions (a gear = settings). **Copy:** a tone suited to the task (NN/g: the cheerful tour in the middle of a fraud claim); each tip, one action. **Behavior:** easy to close and to find again; progressive; this is the kit's place for expressiveness (“rare or first-time”), with the reduced-motion cut. **Accessibility:** A11Y-KBD-07 if modal, APG-06 for coachmarks. **AI anti-patterns:** a tour of 7 coachmarks that blocks the app; confetti on creating the account and on creating each thing. **Check:** a new user can do the main task without closing anything first; review: each help appears at the moment it is needed. **In the set:** a first-use empty with life, `motion/sticky-scroll-reveal`, `ui.moments`. **Sources:** B10 onboarding, empty states; B2 empty states; B14 coachmarks, guided tour, inline hints, blank slate.

### UX-GRAFICO — Which chart for which data

| The data's question | Chart | Source |
|---|---|---|
| How did it change over time? | **line** (markers where there is data); columns if there are few periods | B10 chart types, B17 |
| Which is larger? (magnitude) | **bars** (horizontal if the labels are long) | B10, B17 |
| In what order? (ranking) | **ordered** bars, lollipop | B17 |
| How is it split? (part-whole) | a 100 % stacked bar or a single bar; a pie only with 2–3 parts and one that dominates | B10 dashboards, B17 |
| Are two variables related? | scatter | B10, B17 |
| How is it distributed? | histogram, boxplot | B17 |
| How far from a goal? | diverging bar, bullet | B17; bullet [NV as a recommendation for dashboards, it comes from Few] |
| A compact trend beside a number | sparkline | the kit; B2 index |

**Not when → instead:** pies and donuts to compare values, radial gauges, 3D, treemaps in at-a-glance dashboards → bars; stacked bars to compare segments that share no base → separate bars; color to encode magnitude → length or position. **Copy:** a title that says the conclusion or the question; the unit on the axis or in the title; direct labels better than a legend (A11Y-COL-03). **Behavior:** round 1-2-5 ticks from zero in bars; the current month in accent; a tooltip over the whole band of the column (the kit). **Accessibility:** A11Y-TAB-05, COL-02, COL-03. **AI anti-patterns:** a donut with 9 categories; bars with an axis that does not start at zero; a color gradient as the only encoding; a chart with no alternative table. **Check:** a bar chart's axis starts at 0; the alternative table exists with the same values; review: the table above applied to each chart. **In the set:** `charts.js` (1-2-5 ticks, real HTML axes, the current month in accent, a tooltip per band), `@shadcn/chart`; the `dataviz` skill for palettes. **Sources:** B10 chart types, dashboards; B17.

### UX-KPI — KPIs and dashboards

**Use when:** the user needs to know at a glance whether something requires action (operational) or to analyze calmly (analytical); both on one screen (NN/g). **Not when → instead:** a dashboard as a generic landing with no decision behind it → the work list; open exploration → an analysis view with filters, not tiles. **Copy:** the figure on top, the change beside, the chart below; the figure, its variation and its sparkline come from the **same filtered set**; the variation against the previous period; if the previous is zero, “new”, never a percentage; a differential indicator with sign and arrow, not color alone (Carbon). **Behavior:** the most important top-left; up to 3 charts per row of equal height; the charts respond to the filter; the number that counts on entering (a ticker) only the first time it is seen, never on every navigation (UX-VIDA-2). **Accessibility:** A11Y-TAB-05, MOV-01 (the ticker falls to its value), MOV-02 (live figures pausable), SR-01. **AI anti-patterns:** 8 identical tiles with an icon in a colored circle and an invented green “+12 %”; a variation computed over another filter than the figure; a gauge for a percentage. **Check:** with a filter applied, the sum of the bars equals the KPI's figure and the variation matches (current − previous)/previous; with the previous period at 0 the text is “new”; review: each KPI answers a decision named in the plan. **In the set:** a KPI band (a pill between KPIs, a sparkline whose last point pulses), `motion/number-ticker`, `motion/sliding-number`, `motion/apple-activity-card`, `motion/animated-circular-progress-bar`, `motion/bento-grid`. **Sources:** B10 dashboards; B2 status indicator; `reference/modern-interface.md`.

### UX-REGISTRO — A dense decision record

**Use when:** one record with dozens of fields on which the user decides (approve, ask for more, suspend). The order, top to bottom: a **header that sticks** with the identifier, the state and 4–7 key facts (Salesforce 7, Dynamics 4, Fiori's dynamic header), the decision's actions in it; the **path** of stages; the **exceptions** in one strip right under the header, each linked to its section (cap about 5, then a link to the rest): the user opened the record to find what blocks the decision, so a policy not met, a missing document or a value past its limit is never only found by reading the body; a **section nav** that stays, labels of 1–2 words, the current section marked; the body 2:1, the context column narrow. **Not when → instead:** a record of a dozen fields → one page of groups with no nav; fields compared across records → a table (UX-COLECCION). **Copy:** read-only pairs in a `dl`, 4–6 per group (8 at most), the value heavier than its label; a missing value «—» with its name for a screen reader, never «0»; dates and amounts in the locale; every state that blocks (Failed, Overdue, Missing) is a badge with its word, a mark and its tone (red blocks, amber warns), never plain text in a row; a value past its limit is toned where it is shown, in the header too, with its limit beside it («41.7 % · max 40 %»). **Behavior:** the header compacts on scroll and keeps its facts; anchors land under the bars (`scroll-padding`); one disclosure level inside a section, two at most; secondary sections (documents, history) load when opened or near the viewport; a table over 20 rows paginates. On a phone the header keeps 2–3 facts, the columns stack, the decision goes to a bar at the bottom with 44 px buttons. **Accessibility:** A11Y-COL-02 (state in word + mark), WCAG 2.4.11 (focus not hidden), 2.5.8 (targets ≥ 24 px; 44 on a phone), the decision's answer in a toast and in the record changed in place. **AI anti-patterns:** a hero with the subject's name and nothing to decide on; 60 fields in one card; labels as bold as values; the audit trail on top; a sticky header that takes half the phone; a calm, even record where the policy that fails reads like the ones that pass. **Check:** `ia-check.mjs` (the card's `## Information`): D1 in the first viewport and in view at the end of a long record, values that stand out and read whole, each `signal:` state and each value past its `limit:` toned and one of them in the first viewport, one value column per list, controls of 44 px and bars under 35 % on a phone, disclosures two deep at most, no table in a table. **In the set:** `record.html` (`record.css`, `record.js`): the screen starts from its copy in `design/components/`, and the gate fails `I-set` when it uses fewer than three of its blocks (header, facts, decision, exceptions, checks, sections). **Sources:** Salesforce highlights panel and Path; Dynamics 365 header and business process flow; SAP Fiori object page; Carbon data table and notifications; GOV.UK summary list; Pajamas; NN/g progressive disclosure and tabs; WCAG 2.2.

**UX-REGISTRO-1** — What blocks says what unblocks it: the exception names the limit and what is missing («requested 9 days ago, no answer»), and the action that clears it is one step away. · How T · Check: each exception has its measure, its limit or its age, and a link to the section where it is resolved · Source NN/g error messages; Carbon notifications.

**UX-REGISTRO-2** — A measure against a limit is a bullet graph: the bar is the measure, a tick on the same scale is the limit, so the distance to the limit (or past it) is a length, not two numbers to subtract. · How T · Check: every `.checks__meter` with a limit carries `--limit`, and the tick sits at that fraction of the bar · Source Stephen Few, bullet graph design specification.

**UX-REGISTRO-3** — What passes is folded behind its count («4 rules pass»); what fails and what warns stays open. The count is the answer; the detail is one click away. · How T · Check: no open list mixes passes with failures; the fold's trigger says how many and what · Source NN/g progressive disclosure; GOV.UK task list.

**UX-REGISTRO-4** — A what-if recomputes everything that depends on the value tried —the figure, the ratio, the rules— marks the rule that changes state, and offers the way back to the real value. · How T · Check: moving the value to an end changes the dependent rule's state in words, and the way back restores it · Source NN/g direct manipulation; Carbon slider.

**UX-REGISTRO-5** — A decision with consequence opens a dialog that states it (from what to what, the rule it goes against); one against a rule, or a destructive one, requires a reason, and the reason is written to the history with who and when. A destructive one is an alert dialog that opens on Cancel and does not close on the backdrop. · How T · Check: submitting without a reason shows the field's error and keeps the dialog; with it, the history gains the event on top · Source NN/g confirmation dialogs; WAI-ARIA APG alertdialog; audit-trail practice.

**UX-REGISTRO-6** — Data from another system says as of when: the section that shows an external source names its date and time. · How T · Check: each section fed from outside has its as-of note · Source GOV.UK summary list; NN/g data freshness.

**UX-REGISTRO-7** — One fact lives in two places at most (the header and its section); a third repetition is noise that has to be kept in sync. · How R · Check: count each key figure on the page: two at most · Source NN/g information scent; Tufte data-ink.

## 5. Life: living effects

### UX-VIDA — Marquee, tickers, confetti, beams

**Relation with the kit's rule.** The kit doses life **by frequency** (hundreds of times a day → feedback only; tens → a short response under 200 ms; sometimes → standard motion plus a detail; rare or first time → expressive). NN/g reaches the same axis from evidence: the third question of its checklist is “how many times does the user see this animation in a session?”, and repetition makes any animation tedious (B10 animation). Two more axes it adds: **where the attention is** when it happens (peripheral movement steals attention from the task) and **what triggers it** (what the user triggers may be fast; what appears alone must be slow and without displacement, because what moves from place attracts more than what appears in place).

| Effect | Adds when | Distracts when | Source |
|---|---|---|---|
| **Marquee** (logos, ribbon) | a landing or showcase; social proof that is not read | on a work screen: continuous peripheral movement; over 5 s with no pause breaks 2.2.2 | B15, B10 |
| **Number ticker** | the first time a figure is seen in a session; celebrating a total | on every navigation or filter (repetition); if the figure is read while it counts (the intermediate value is false) | B10 |
| **Sliding number** | a figure that **changed by the user's action** (it explains the change) | figures that update by themselves every second (auto-update, 2.2.2 with no 5 s exception) | B10, B15 |
| **Confetti** | a rare, significant moment (the first invoice) | any repeatable action; errors; with no equivalent text | the kit `ui.moments`; B10 |
| **Beam / border beam** | **one lap** over the only element that needs attention | in a loop, or on several elements at once | the kit; B10 |
| **Animated beam** (connections) | explaining a relation (integration A → B) in configuration or showcase | as a permanent decoration of a dashboard | B10 |
| **Spotlight / magic card** | cards that can be pressed (it says “this answers”) | cards that only show figures (the kit: tilt on figure cards is out) | the kit |

**Not when → instead:** on what is used hundreds of times (palette, tooltip, menu) → feedback only; over amounts: text that types itself or scrambles (the kit's “what stays out”) → a static figure or a short sliding number; as the only signal of something (success, error) → always with its text toast. **Accessibility:** A11Y-MOV-01, MOV-02, MOV-03, APG-09 (a marquee is a carousel); detector A11Y-IA-13. **AI anti-patterns:** a logo marquee and background meteors on the billing dashboard; a number ticker that counts from 0 again each time a filter changes; confetti on saving a draft; a border beam in a loop over three cards at once; an infinite shimmer on the primary button. **Check:** with `prefers-reduced-motion: reduce` no element has `animation-iteration-count: infinite` nor transforms position and tickers show the final value; the marquee has a named pause button and stops on `visibilitychange`; navigate to Home, leave and return: the ticker does not count again; with the moment disabled the first invoice shows the toast and no confetti. **In the set:** `life.js`/`life.css`, `ui.moments` (four moments), `motion/marquee`, `motion/number-ticker`, `motion/sliding-number`, `motion/animated-beam`, `motion/magic-card`, `effects.css` (`.beam[data-attention]`). **Sources:** B10 animation; B15 2.2.2; the kit `reference/modern-interface.md` and `reference/components.md`. The marquee on the Home screen of the component set, mounted with `pauseOnHover` and no `control` on a work screen, is fixed by the set's own card.

**UX-VIDA-1** — Every loop pauses off screen and with a hidden tab; whatever moves for more than 5 s has a pause control or stops by itself (A11Y-MOV-02, WCAG 2.2.2). · How T · criterion I25 · Check: the marquee has a named pause button and stops on `visibilitychange`; no loop without pause · Source B15, B10.

**UX-VIDA-2** — An “entry” effect (ticker, blur-fade, arrival shimmer) runs **once per session** per element, not on every visit to the route. · How T · criterion I25 · Check: navigate to Home, leave and return: the ticker does not count again · Source B10.

**UX-VIDA-3** — Expressive moments go one at a time, can be disabled one at a time, and with reduced motion become a fade. · How T · criterion I25 · Check: with the moment disabled the first invoice shows the toast and no confetti; with `prefers-reduced-motion: reduce` the ticker shows its final value · Source B10, the kit.

**UX-VIDA-4** — The accessible value of an animated figure is the final one from the first frame (`aria-label` or hidden text with the final value), not the intermediate ones. · How T · criterion I25 · Check: read the figure's accessible name during the animation: it is the final value · Source B10.

## The decision trees

**Which overlay?** Does the user need the page behind while using this? Yes → is it a detail/edit of a list item? Yes → a drawer / non-modal side panel (split view); no → an anchored popover (little content, 1–3 actions), on mobile a sheet. No → is it critical or does it block what the user started? Yes → a short task (one screen, two actions at most)? yes → a modal (an alert dialog if there is potential loss), no → a new page. No → information with no action → a toast / inline (no overlay); a complex flow or a large table → a new page. Always: a modal does not open another (except “Discard changes?”); one popover at a time.

**Which selection control?** More than one allowed? Yes → few options (under about 8) or all must be seen → checkboxes (with an exclusive “None”); many → a multi combobox / a listbox with search. No → binary and applied on the spot → switch; binary and applied on submit → checkbox (or 2 radios if both options need a name); changes a view or an immediate parameter with 2–5 short options → segmented; a form with under 5 options → vertical radios; 5–15 options, a secondary field, little space → select; 15+ or a known list (country, customer) → a combobox with typing; a value the user knows (a year, a quantity) → input; an approximate value in a range → a slider plus an input if the number matters. Default: settings → the current value marked; a question with consequence → none marked.

**Which feedback?** About a field the user filled → an inline error next to the field (+ a summary on submit). The immediate answer to a user action: the result already shows → nothing (or the button's state, “Saved ✓”); a brief success → a toast that goes by itself (4–7 s) with equivalent feedback in place; it offers undo → a toast with an action of 10 s or more + Undo also outside the toast; it failed → inline / a section message on the affected element (not a toast that leaves). The system's and affects the whole app → a banner (one, until it stops applying). It happened in the background or someone else did it → a notification + a notification center. It demands a decision now → a modal.

**Which loading?** How long does it take (p90)? Under 0.4 s → nothing; the action's feedback. 0.4–1 s → an indicator with a delay of about 300 ms (it does not flash). 1–10 s → loads a page or region of known shape → a skeleton with the real layout; an action or a module → an inline spinner (a button in loading). Over 10 s → a progress bar with % or “n of N”, an estimate and Cancel. Minutes → background + a notification on finishing. Never: “No results” while loading; a skeleton in menus or toasts; a spinner for uploads.

**Which collection view?** Are the items homogeneous and compared by attributes (amounts, dates, states)? Yes → 3 or more attributes or batch actions → a table (on mobile a two-line card); no → a list. No (heterogeneous, to browse) → cards. How many? The user searches or compares → pagination (in the URL, keeping position on return); browsing with no goal and no footer needed → infinite scroll; a middle point / mobile / the footer matters → “Load more”.

## The 15 most common errors of choosing a pattern, in AI-generated UI

Ordered by frequency observable in generated UI × cost to the user. 1 **Modal for everything** (UX-OVERLAY; a “a modal does not open another” test). 2 **Toast for errors** (UX-FEEDBACK-1). 3 **Confirmation on every deletion** instead of undo (UX-CONFIRMAR). 4 **A switch in a form with “Save”** (UX-CHECK-SWITCH-1). 5 **Several filled primaries** per view (UX-BOTON-1). 6 **A select for 2–4 options**, or of 200 without search (UX-SELECCION). 7 **A dashboard of identical cards** with invented or incoherent KPIs (UX-KPI, UX-COLECCION). 8 **Errors on leaving an empty field** or while typing (UX-INPUT-1). 9 **A tooltip with essential information** or as a button's name (UX-AYUDA). 10 **A full-screen spinner** for short loads; “No data” before it arrives (UX-CARGA, UX-VACIO-1). 11 **Tabs for everything** (UX-SECCIONES). 12 **Pies, donuts and gauges** in dashboards (UX-GRAFICO). 13 **Expressive effects on what is frequent** (UX-VIDA). 14 **Drag as the only way** (UX-ARRASTRE-1). 15 **Onboarding with a tour/modal on first login** (UX-ONBOARDING). Mentions that did not enter the top: `role=menu` for navigation (UX-MENU), breadcrumbs in a one-level app (UX-MIGAS), infinite scroll in tables (UX-PAGINACION), a wizard for 5 frequent fields (UX-WIZARD), a disabled button with no reason (UX-BOTON-4).
