# Code patterns: when they pay and when they are overengineering

**When it is read:** when the card brings a design decision (a new abstraction, an interface, a
repository, a factory, a bus, a state machine, a layer). **How:** only the sheet of the pattern the card touches, with `Read` and a line range of its heading;
never whole. `card.md` names the rule IDs that apply, and the `builder` receives those IDs and their
ranges. This reference complements `rules/architecture.md` (the five rules, the ladder “Before writing a new
piece” and “What not to do”, which link here), the criteria D4–D7, K4 and K5, `reference/architecture.md`,
`reference/database.md` (module data) and `reference/errors.md`; when a sheet touches something already there it cites it by
ID. **Libraries and tools are options, not obligations.** **[NV] marks guidance not verified**: a hypothesis,
never the only evidence of a `meets`; **[V sec]** was checked in a secondary source quoting the primary one.
How each rule is checked: `C` a command (a grep or a tool: it prints something or not), `T` a test, `J`
judgment (a reviewer with concrete questions who leaves written evidence). **The ladder** is the five steps of
`rules/architecture.md`: (1) does it already exist in the repo, (2) the standard library, (3) the platform,
(4) a dependency that is already there, (5) only then, the minimum that works. The commands assume `rg` and
code under `src/`; the ones marked [tried] were run over a sample tree with known positives and negatives and
gave the expected result; over a real repo they are heuristics: each finding is looked at, not deleted blindly.
Source numbers `Bn` are in Sources. Each sheet gives the rule as: use it **only when** its smell is present,
and what is simpler otherwise.

**The common principle.** A pattern answers a **force that is already in the code or in the requirement**,
not one that might appear. Kerievsky (B5) arrives at patterns by refactoring; Metz (B14) and Abramov (B16)
show the cost of the abstraction that comes early; Yagni (B3) names the **cost of carrying it**. The kit says
it in “What not to do”: do not introduce an abstraction until there is a concrete reason; two uses are not a
pattern. The question of every sheet is: **what is the force, where is it written, and what happens if I
remove it?**

## 1. The GoF patterns of real use in TS/Node and the front

**PAT-STRATEGY** — Strategy: use it only when the same `switch`/`if` over one discriminant is repeated in **several** places (Switch Statements, B6) or someone outside chooses the variant (configuration, plugin, client). With two or three stable variants and a single `switch`, a function is enough (B6, B12): a discriminated union plus an exhaustive `switch`, or a map of functions. · How J+C · criterion D6 · Check: [tried] interfaces with at most one implementation and no fake in tests (C12); `rg -n "interface \w+Strategy|class \w+Strategy" src/` and count implementations; is there more than one `switch` over the same field? does anyone external pick the variant? If both answers are no, it is surplus. TS `type Shipping = { kind: 'pickup' } | { kind: 'moto'; km: number }` with `switch (e.kind)` and `const never: never = e` in `default`; Strategy would pay if the rates came from a plugin per customer (`Record<string, (e) => number>`) · Source B1, B5, B6, B12, B17.

**PAT-FACTORY** — Factory function / Factory Method / Abstract Factory: use it only when the concrete type is decided at run time, when building demands steps and validations the caller should not know, or when the constructor cannot express “create or reject” or return an existing instance (B6). A `XFactory` class with a single `create()` that does `new X(args)` is pure indirection; Factory Method with “creator” subclasses is almost never needed in TS (B12). Instead: an exported `createX()` function (Replace Constructor with Factory Function, B4), a `static create()` in the class itself, or pass the class as a value. · How J+C · criterion D6 · Check: [tried] `rg -n "class \w+Factory\b" src/` and for each: does it have more than one possible return type or logic besides the `new`? how many callers build this? TS `static create(s: string): TaxId | null { return checkDigitOk(s) ? new TaxId(s) : null; }` with a private constructor. See PAT-DDD-FACTORY for aggregates · Source B1, B4, B5, B6, B12.

**PAT-BUILDER** — Builder: use it only for a step-by-step construction with many optional parts or several representations, a tree built in several steps, or a public fluent API where the order of steps matters and is guided by types. The “telescoping constructor” is solved in TS with a typed **options object** with defaults (Introduce Parameter Object, B4); a `XBuilder` with `withA().withB().build()` that only assigns fields is classitis (B13). · How J+C · criterion D6 · Check: [tried] `rg -n "class \w+Builder\b" src/`; does any step do more than assign? does `build()` validate? If not, an options object; in tests, a function `anOrder(overrides)`. A query builder (Kysely/Knex) is a legitimate builder: each step changes the available type · Source B1, B4, B5, B6, B12.

**PAT-ADAPTER** — Adapter: use it only when third-party types (Stripe, S3, an HTTP client) show up in the domain or in several modules, two classes do the same with different interfaces, or packages that are not yours are mocked in tests. If the “service” is your own code, it is sometimes simpler to change the service class (B6); wrapping the standard library, the chosen framework or the design system's primitives is indirection with no decision to hide (`reference/architecture.md` ARQ-07, “does not apply”). Instead: change the own code, or use the SDK directly if it is used in a single file and embodies no decision that can change. · How C+J · criterion D15 · Check: `rg -l "from 'stripe'" src/` returns a single file; the adapter has no `if` over business concepts; is the adapted thing foreign or does it embody a decision that changes? If not, it is surplus. TS `export const stripeCharger = (stripe: Stripe): Charger => ({ charge: async (m, customer) => (await stripe.paymentIntents.create({ amount: m.cents, currency: m.currency, customer })).id })` in the only file that imports `stripe` · Source B1, B5, B6.

**PAT-FACADE** — Facade: use it only when callers coordinate five objects of a subsystem in the same order in several places, or there are deep imports into another module. With modules a facade is invisible, “just export the names that form the interface” (B12): in TS the module's **public index** is the facade. A facade class that forwards each method 1:1 is Middle Man (B6) and a shallow module (B13). Instead: an `index.ts` that exports only what is public; Remove Middle Man (B4). · How C+J · criterion D4 · Check: [tried] methods that only forward to the same name (C14); is the interface smaller than what it hides? TS `export { registerCustomer, findCustomer } from './application/use-cases';` in `customers/index.ts` and nothing else. `rules/architecture.md` §Module boundaries; ARQ-04 · Source B1, B4, B6, B12, B13.

**PAT-DECORATOR** — Decorator: use it only when the same logging/cache/measurement block is copied around several calls, or an explosion of subclasses by combination of extras (Move Embellishment to Decorator, B5). A single extra in a single place is written inline. Verified cons: a wrapper is hard to remove from the stack, behavior may depend on order (B6). Retry and circuit breaker belong to a single layer of the stack (`reference/errors.md` ERR-RES-03). Instead: a higher-order function (`withCache(fn)`) or the framework's middleware (ladder 3–4) before a wrapping class. · How J+C · criterion D6 · Check: how many use points does the wrapper have? does the framework already bring a middleware/interceptor for it? TS `const withTiming = (name, fn) => async (...a) => { const t = performance.now(); try { return await fn(...a); } finally { metrics.observe(name, performance.now() - t); } }` · Source B1, B5, B6.

**PAT-OBSERVER** — Observer / events / in-process pub-sub: use it only when a function, on finishing, calls by hand three foreign modules that are not its responsibility (Replace Hard-Coded Notifications with Observer, B5), or in the UI a component has to learn of something that happens far in the tree. With one known subscriber in the same module, a direct call. An in-process event bus hides the flow (who reacts is not visible), the notification order is not guaranteed (B6), a subscriber's errors do not reach the emitter and are lost if the process dies: **an in-memory event is not a durable message** (that is PAT-OUTBOX). In the front, props and callbacks before a global bus (ARQ-13). Instead: a direct call; the platform's `EventTarget`/`CustomEvent` (ladder 3); the store the repo already has. · How C+J · criterion D6 · Check: [tried] `rg -n "new EventEmitter\(|class \w*EventBus|mitt\(" src/`; per event count subscribers (`rg -n "\.on\('name'|addEventListener\('name'"`): if it is one and in the same module, a direct call; does something depend on the subscriber running for sure? then it is not Observer, it is outbox/queue. See ARQ-13, ARQ-14, ERR-CAP-10 · Source B1, B5, B6, B12, B19.

**PAT-COMMAND** — Command: use it only when an operation is treated as data: queued, scheduled, logged, undone; undo/redo; a queue or a log of operations; a dispatcher with a giant `switch` by action name (Replace Conditional Dispatcher with Command, B5). If it is only executed at the moment, it is a function (Fowler's Replace Command with Function, B4; Norvig, B12). A `CommandBus` plus a `CommandHandler` per use case in a CRUD is “What not to do”. Instead: the use case's function; for UI undo, a reducer with a history of states. · How J+C · criterion D6 · Check: [tried] `rg -n "(Command|Query)(Handler|Bus)\b" src/`; is any command queued, persisted, undone or retried? If none, they are functions. TS `type Action = { kind: 'move'; id: string; to: Point } | { kind: 'delete'; id: string }` and `const undo = (history) => history.slice(0, -1)` · Source B1, B4, B5, B6, B12.

**PAT-STATE** — State / state machine: use it only when conditionals over `state` repeat in many methods (Replace State-Altering Conditionals with State, B5), booleans can contradict each other (`isSending && isSent`, B18) or the code allows invalid transitions. “It can be excessive if the machine has few states or rarely changes” (B6); a class per state is almost always too much in TS. Instead: a union of literals plus a **table of transitions** plus a function that validates; in UI, `useReducer` with a single `status`. A statecharts library (XState) only if it is already there or there are hierarchical/parallel states [NV: not evaluated]. · How J+C+T · criterion D6 · Check: how many states and how many methods change by state? with under about 5 states and behavior in 1–2 methods the table is enough; `rg -n "class \w+State\b" src/`; a test per forbidden transition. TS `const transitions: Record<State, readonly State[]> = { draft: ['sent'], sent: ['approved','rejected'], approved: [], rejected: ['draft'] }`. See ERR-DES-03, ARQ-13 · Source B1, B5, B6, B12, B18.

**PAT-TEMPLATE-METHOD** — Template Method: almost never in TS; only when two classes have the same skeleton with differences in specific steps (Form Template Method, B5). Cons: it can violate Liskov by suppressing a default step and is harder to maintain the more steps it has (B6); Norvig: invisible with first-class functions (B12); GoF itself prefers composition to inheritance (B1); React found no use for component hierarchies (B18). Instead: a function that receives the varying steps as functions; Replace Subclass/Superclass with Delegate (B4). · How C+J · criterion D6 · Check: [tried] abstract classes with at most one subclass (C13); `rg -n "abstract class" src/` and review each; does any subclass override a step to do nothing? TS `const exportRows = async <T>(rows, serialize: (r: T) => string, dest) => { for await (const r of rows) dest.write(serialize(r) + '\n'); }` · Source B1, B4, B5, B6, B12, B18.

**PAT-COMPOSITE** — Composite: use it only to treat a leaf and a group of leaves the same (menus, nested permissions, expressions, folders): code that distinguishes “one or many” in every caller (Replace One/Many Distinctions with Composite, B5) or an implicit tree built with strings or untyped nested arrays. With no real recursion (two fixed levels) an array is enough; in UI the components already are composites (`children`, `<slot>`). Instead: a recursive type plus a recursive function. · How J · criterion D6 · Check: is the depth arbitrary? do 2 or more operations walk the tree? TS `type Node = { kind: 'file'; bytes: number } | { kind: 'folder'; children: Node[] }` · Source B1, B5, B19.

**PAT-PROXY** — Proxy: use it only for an expensive resource that is almost never used, or remote calls that must look local. JS's `Proxy` for “magic” (properties that fire queries, implicit validations) hides effects and breaks debugging; ORMs already bring lazy-loading proxies that cause N+1 (PAT-LAZY-LOAD). Instead: an explicit function (`loadX()`), memoization (`??=`), the HTTP client's or the framework's cache. · How C+J · criterion D6 · Check: `rg -n "new Proxy\(" src/` each with a line of why; can a reader of the caller see there is I/O there? TS `let client; export const getClient = () => (client ??= createClient());`. K10; DB-IDX-06 · Source B1, B12, B20.

**PAT-SINGLETON** — Singleton, and why almost never: the smell that would justify it is a resource that **must** be unique per process (a connection pool, a client with connection state) and is expensive to create. Verified cons: it breaks single responsibility, hides dependencies, needs care in concurrency and “makes unit testing harder” (B6); Kerievsky has **Inline Singleton** (B5). In Node a module already is a unique instance per process (module cache) [NV: documented Node behavior, not opened]. Instead: create the instance once at the composition root (`main.ts`) and pass it as a parameter, or export the instance from the module if it need not be replaced in tests. · How C+T · criterion D6 · Check: [tried] `rg -n "static (getInstance|instance)\b|private static instance" src/` returns 0, or each with its why; do the tests have to “reset” the singleton between cases? If yes, it is already costing. D6: what is injected to test —the clock, the storage— does not count as speculative generality; rule 3 of the architecture (what comes from outside enters as a parameter). TS `const pool = new Pool({ connectionString: env.DATABASE_URL }); const app = createApp({ orders: ordersRepo(pool), clock: () => new Date() });` · Source B1, B5, B6, B12.

**PAT-ITERATOR** — Iterator / generators: use it only to walk a collection or stream without exposing how it is made, or produce values on demand; the smell is loading everything in memory to walk it (API pagination, big files, database rows) or nested callbacks for “the next one”. Do not write it by hand: JS brings the `[Symbol.iterator]`/`next()` protocols, `for…of`, spread, generators and their async version (B19); Norvig: invisible (B12). A `class XIterator { hasNext(); next() }` is rewriting the platform. Instead: `function*`/`async function*` and `for await`; an `Array` if the data is already in memory and small. · How C+J · criterion D6 · Check: `rg -n "hasNext\(\)|class \w+Iterator\b" src/` returns 0; ladder 2; ERR-RES-09 (what grows has a cap: the generator does not accumulate). TS `async function* pages(fetchPage) { let cursor; do { const r = await fetchPage(cursor); yield* r.items; cursor = r.next; } while (cursor); }` · Source B1, B12, B19.

**PAT-MEDIATOR** — Mediator: use it only when many components talk to each other in pairs and the coordination has to be centralized (N components of a form/screen where each knows several siblings). “Over time a mediator can become a God Object” (B6). In the front, the common ancestor that holds the state **is** the mediator (lifting state, B18, ARQ-13); a backend “mediator” library (`mediator.send(new X())`) to dispatch to a single handler is Command plus indirection. Instead: lift the state to the common parent; a reducer; a direct call to the use case. · How C+J · criterion D6 · Check: `rg -n "class \w*Mediator|mediator\.send\(" src/`; does any handler have more than one possible dispatcher? does the mediator carry business logic (it should not)? · Source B1, B6, B12, B18, B20.

## 2. PoEAA

**PAT-TRANSACTION-SCRIPT** — Transaction Script, the baseline: one procedure per request that calls the database directly or through a thin wrapper (B2) is right for simple business logic, mostly validate-save-read: a CRUD. Domain model starts to pay when the same rules repeat across several scripts or there are invariants that cross several operations over the same entity; a “domain model” with no behavior is a Transaction Script in disguise that pays the domain's costs without its benefits (Anemic Domain Model, B3). Choosing between both by complexity is in the book [NV]. · How J · criterion D6 · Check: is the card a CRUD? then it is this (“If the card is a CRUD, deliver a CRUD”); are there domain classes with no methods and services with all the logic? then either the domain is enriched or the script is admitted without the ceremony. TS `export async function registerCustomer(db, input) { const c = validate(input); return db.insert('customers', c); }`. Rule 1 (the controller does not talk to persistence): the script lives in `application` · Source B2, B3.

**PAT-REPOSITORY** — Repository: use it only when ORM queries are scattered in controllers, services and views, the same query is written twice, or the domain imports the ORM. Fowler: it pays “when there are many domain classes or heavy queries” (B2); Evans: “**only for the aggregate roots that really need direct access**” (B9). The kit: **no generic repository** (`findOne(criteria)`, `BaseRepository<T>`): a domain one with methods that say the intent (`findByTaxId`). A repository that wraps 1:1 an ORM that already is one (Prisma, TypeORM `Repository<T>`) is Middle Man. Instead: in a CRUD, the ORM's client behind the module's data access layer (DB-OWN-05), with no interface. · How C+J · criterion D6 · Check: [tried] `rg -n "class \w*(Base|Generic|Abstract)Repository|Repository<\w+>" src/` returns 0; methods that only forward to the ORM (C14); does it have an in-memory fake used by tests? does each method have a caller? is it per aggregate root or one per table? D6: the test fake justifies the interface. TS `export type Customers = { byTaxId(c: TaxId): Promise<Customer | null>; save(c: Customer): Promise<void> }` · Source B2, B9, B11.

**PAT-UNIT-OF-WORK** — Unit of Work: use it only to keep the list of objects affected by a business transaction and write them together, coordinating concurrency (B2); the smell is several `save()` of the same use case that must be atomic and today are not. Writing it by hand almost never: ORMs with tracking (TypeORM `EntityManager`, MikroORM, EF Core, Hibernate) **are** a unit of work [NV: their docs were not opened], and in those that are not, the database transaction is enough. Instead: `db.transaction(async (tx) => { … })` in the use case, passing `tx` to the repositories. · How C+T · criterion D6 · Check: `rg -n "class \w*UnitOfWork" src/` returns 0 unless with a written reason; a test: the rollback leaves everything as it was (ERR-DES-05); DB-TX-05 (nothing external inside the transaction). TS `await db.transaction().execute(async (tx) => { await orders(tx).save(p); await stock(tx).discount(p.items); });` · Source B2.

**PAT-ACTIVE-RECORD** — Active Record versus Data Mapper: Active Record, the object wraps a row and saves itself; Data Mapper, a separate layer moves the data and the object does not know there is a database (B2). Data Mapper pays when there are rich domain rules to test without a database or the model and the schema diverge (an aggregate in several tables, embedded value objects). Data Mapper plus domain entities plus mappers for a CRUD duplicates each class (ORM model, entity, DTO) with no rule to protect; Active Record with heavy business logic ties the rules to the database and slows the tests. Instead: follow what the repo's ORM already does (K11); for a CRUD, the ORM model behind the data access layer; when rules appear, extract them to pure functions that receive plain data. · How J+C · criterion D6 · Check: count classes per concept (ORM model, entity, DTO, mapper): more than 2 with no domain invariant is ceremony; `rg -n "toDomain|toPersistence|fromEntity" src/` and see whether each mapping transforms something or copies field by field. Rule 3 of the architecture applies **if there is a domain**; ARQ-03 · Source B2, B3.

**PAT-SERVICE-LAYER** — Service Layer / use cases: use it only to define the application's edge as a set of operations that coordinate domain, transaction and response (B2): the same interaction duplicated across several clients (HTTP, CLI, queue, cron), or controllers that talk to the database (rule 1). The layer must be **thin** and coordinate; if all the logic lives there and the entities are bags of getters, it is the anemic-domain anti-pattern (B3). A service per entity with `create/get/update/delete` that only forwards to the repository is Middle Man (B6, D4). Instead: in a CRUD, a function per use case that validates and calls data access. · How C+J · criterion D4 · Check: [tried] forwarding methods (C14); rule 5 (if explaining the service takes more than two “and”s, they are two). TS `export async function approveOrder(dep: { orders: Orders; clock: () => Date }, id: string) { … }` · Source B2, B3.

**PAT-DTO** — Data Transfer Object: use it only to move data in an expensive remote call in a single trip (B2) or to fix the contract of a boundary; the smell is ORM entities returned as they are by the API (leaking internal fields) or a public contract that changes when the table changes. **Inside the process**: “not only do you not need them, they are harmful”; do not add them for a future distribution (B3); the exception is a presentation facade when the screen differs a lot from the domain. Instead: at the HTTP edge, the validation schema (zod/valibot) **is** the DTO (the inferred type); inside, the domain's types. · How C · criterion D6 · Check: [tried] `rg -n "class \w+Dto\b" src/ --glob '!**/http/**' --glob '!**/api/**'` returns 0 (adjust to the repo's edge directory); ARQ-03; K8. TS `export const NewCustomer = z.object({ taxId: z.string(), name: z.string().min(1) }); export type NewCustomer = z.infer<typeof NewCustomer>;` · Source B2, B3.

**PAT-GATEWAY** — Gateway: use it only to encapsulate access to an external system behind a common object interface so changing provider touches only the gateway (B2); the smell is `fetch`/SDK calls to the same provider in several files with the provider's error handling repeated. Same as Adapter: not for the standard library nor for something used in one place that cannot change. In practice the Gateway is the outgoing adapter toward an external system. · How C · criterion D15 · Check: `rg -l "<provider host or SDK>" src/` returns a single file; timeouts and the failure policy in that file (D8); ARQ-07; ERR-LAY-02 (the gateway translates the provider's errors) · Source B2.

**PAT-MONEY** — Money: money is not a first-class type in any common language, and mixing currencies and rounding “loses cents” (B2); the smell is `number` for amounts, `toFixed(2)` in rules, sums across different currencies, splits (installments, proration) that do not add up. With one currency and only showing amounts that arrive computed, integers in cents (or `bigint`) and `Intl.NumberFormat` to show are enough (ladder 2). Instead: integer cents plus currency in the type; a money library if the repo already has one. A value object with the amount as an integer in the minimum unit plus currency; splits that assign the remainder. · How C+T · criterion P8 · Check: ``rg -n "toFixed\(|parseFloat\(" src/**/domain/`` returns 0; `rg -n "(price|amount|total)\w*\s*:\s*number" src/`; a test: splitting 100 in 3 adds 100; DB-MOD-05 (money in `numeric`, never `float`). TS `export type Money = Readonly<{ cents: bigint; currency: 'ARS' | 'USD' }>` · Source B2, B3.

**PAT-SPECIAL-CASE** — Special Case / Null Object: `null` defeats polymorphism and forces repeated checks in each caller (B2); the smell is the same `if (!customer) { name = 'Guest'; discount = 0 }` in several places. In strict TS, typed `null`/`undefined` already force handling the case and `?.`/`??` solve it in one line; a Null Object can **hide** a real error (a customer that had to exist and does not). Instead: `T | null` plus explicit handling; Special Case only when the special case has business behavior of its own (a guest customer, a free plan). · How J · criterion D6 · Check: is the special case a business concept or an error? If it is an error, ERR-DES-02/ERR-TAX-03. K1 (strict mode). TS `const GUEST: Customer = { id: 'guest', name: 'Guest', discount: () => 0 }` · Source B2, B4, B5.

**PAT-IDENTITY-MAP** — Identity Map: load each object only once per business transaction so there are no two copies of the same row (B2); the smell is two instances of the same record modified in a use case and the last one overwrites the first. Writing it by hand almost never: it is part of ORMs with a unit of work [NV]; with explicit queries and short use cases the problem does not appear. Instead: load once and pass the object; a DataLoader per request if the problem is repeated reads (and N+1). · How C+J · criterion D6 · Check: ``rg -n "class \w*IdentityMap|new Map<string, \w+>\(\)" src/**/infra/``; does any use case load the same entity twice? Ladder 4 · Source B2.

**PAT-LAZY-LOAD** — Lazy Load, and the N+1: do not fetch data until used (B2) so loading an object does not drag its whole graph; the smell is lists that load relations nobody shows. Not in collections: a lazy relation accessed inside a loop or a serializer is **one query per row (N+1)**, which the ORM hides. Instead: explicit loading per use case: a join, `IN (…)`, the ORM's `include`/`with`, or a DataLoader. · How T+C · criterion P10 · Check: a test that counts queries per request (DB-IDX-06); ``rg -n -U "for\s*\(.*\)\s*\{[^}]*await\s+\w+\.(get|find|load)" src/`` as an alert. TS `await db.selectFrom('orders').innerJoin('customers', …).where(…).execute()` instead of `for (const p of orders) await p.getCustomer()`. K10 · Source B2.

## 3. Tactical DDD

**PAT-ENTITY** — Entity: an object that is distinguished by identity and continuity over time, not by its attributes (B9): two records with the same data that are different things (two homonymous customers), rules about the life cycle. Do not model as an entity what is a value (an address, a date range); do not put in the entity everything that is not identity: Evans asks to keep it “simple and focused on continuity and identity”. Instead: a value object; in a CRUD, the row type. · How J · criterion none · Check: is equality by id? does it have life-cycle rules? Rule 2 (the domain carries the name, not the appearance); rule 3. TS `export type Order = Readonly<{ id: OrderId; state: State; items: readonly Item[] }>` with functions that validate transitions · Source B9.

**PAT-VALUE-OBJECT** — Value Object: a concept defined by its attributes, immutable, with equality by value and its own validation (B3, B9); the smell is **Primitive Obsession** (B6): tax id, email, currency, percentage as `string`/`number` validated in several places, Data Clumps (`from`/`to` that always travel together), aliasing bugs from mutating a shared object. A datum with no rules or operations (a free name) needs no type of its own. Instead: a *branded type* plus a parse function; `Readonly<>` and `as const` (Replace Primitive with Object, B4). · How C+J · criterion none · Check: ``rg -n "(taxid|email|currency|phone)\w*\s*:\s*string" src/**/domain/`` and count where the format is validated: more than one place means the value object is missing; does the value have rules or operations? ERR-DES-03; K6. TS `export type Email = string & { readonly __brand: 'Email' }` with `parseEmail(s): Email | null` · Source B3, B4, B6, B9.

**PAT-AGGREGATE** — Aggregate: guarantee invariants that span several objects and define the unit of load, save and transaction (B3, B9); the smell is a rule that involves the head and its parts (an order's total = the sum of items with a credit cap) broken because someone modifies a part directly, or concurrency conflicts on objects that share no invariant. Not large aggregates “just in case” (a customer with all their orders): Vernon asks for **small aggregates around real invariants**, references to other aggregates **by identity** and eventual consistency outside the boundary (B11). Without an invariant between objects there is no aggregate: there are entities. Instead: independent entities referenced by id. · How J+C · criterion D12 · Check: name the invariant that justifies the boundary (if it cannot be written, there is no aggregate); does any transaction modify two aggregates? (it should be a justified exception, B11); imports of the aggregate's internal parts from outside it. ARQ-04; DB-TX-03. TS `export const addItem = (o: Order, i: Item, cap: Money): Order | DomainError => …` the only entry to touch items is the root · Source B3, B9, B11.

**PAT-DOMAIN-SERVICE** — Domain Service: a domain operation that is not the natural responsibility of an entity or a value object (B9); the smell is an entity that has to “borrow” data from another to do its job (Feature Envy, B6), or a rule that coordinates two aggregates. Not as a dump for all the logic (anemic domain, B3), nor with state, nor with I/O (that is application or infrastructure). A “service class” with a single stateless method is a function. Instead: a pure function of the domain module; a method on the entity if the rule is its own. · How J+C · criterion D12 · Check: does it have a name from the business's language? is it pure? ``rg -n "import .* from '.*(infra|http|sequelize|prisma|axios)" src/**/domain/`` returns 0. Rules 3 and 5; D2. TS `export const canTransfer = (from: Account, to: Account, m: Money): boolean => …` · Source B3, B6, B9.

**PAT-DOMAIN-EVENT** — Domain Event: record something significant that happened in the domain, decouple reactions, audit (B3, B9); the smell is other modules or services needing to learn of a change (an order paid → billing, stock, mails), or the business asking for a history of facts. Not inside one module to call a function that could be called directly, nor as a substitute for a transaction. Fowler: its own architectural style, awkward at first, a proliferation of almost equal types (B3). An event emitted in memory before the commit is lost or lies (DB-TX-06). Instead: a direct call between modules through their public index; if it must survive a crash, outbox. · How J+C · criterion none · Check: who consumes each event and is it in another module? events with no subscriber are dead code (K5). TS `type OrderPaid = Readonly<{ kind: 'OrderPaid'; orderId: string; occurred: string; recorded: string }>` (immutable, with the instant it occurred and was recorded). DB-TX-06; ARQ-11 · Source B3, B9.

**PAT-DDD-FACTORY** — Factory (DDD): create a whole, consistent aggregate when creation is complicated or reveals the internal structure (B9); the smell is the caller assembling internal parts of the aggregate and being able to leave it invalid. If creating is validating and assigning, a static `create()` on the root is enough (PAT-FACTORY). Instead: a creation function that returns the aggregate or an error. · How J · criterion none · Check: as PAT-FACTORY · Source B9.

**PAT-SPECIFICATION** — Specification: separate the criterion (“what qualifies”) from the evaluated object, for selection, validation or on-demand construction (B10); the smell is the same business condition (“delinquent customer”) written in a front `filter`, in a `WHERE` and in a validation, or criteria that the user combines and saves. Evans and Fowler: do not use it as an object of flexible attributes; reconsider if `isSatisfiedBy` is not used, the protocol grows or it represents a real entity. A framework of combinable specifications for three fixed filters is overengineering. Instead: a named predicate (`isDelinquent(c)`) and, if needed in SQL, a function that returns the query builder's condition; the composed form (and/or/not) only when the user builds criteria. · How J · criterion D5 · Check: is the criterion used in 2 or more places, or does the user combine it? TS `export const isDelinquent = (c: Customer, today: Date) => c.debt.cents > 0n && daysBetween(c.due, today) > 30` · Source B10.

## 4. Integration

All of these presuppose **several processes or services with their own state** and messaging. In a monolith with one database the local transaction solves almost everything (`reference/architecture.md` ARQ-10: a modular monolith by default).

**PAT-OUTBOX** — Transactional Outbox: update the database and publish a message atomically without 2PC (B8); the smell is `await db.save(); await broker.publish()` (if it falls between them the message is lost) or publishing inside the transaction (if it rolls back, the message has already gone out). Not if there is no broker nor another service that consumes, or if the effect can be synchronous and inside the same database. Instead: a local transaction; a jobs table in the same database with `SKIP LOCKED` (DB-ENG-02). The named risk: the relay can publish **more than once** → idempotent consumers. · How T+C · criterion P13 · Check: a test: a rollback leaves no outbox row; `rg -n "publish\(|\.emit\(" src/` inside `transaction` blocks returns 0. DB-TX-05/06 are not repeated here. TS `await db.transaction().execute(async (tx) => { await orders(tx).save(p); await tx.insertInto('outbox').values({ kind: 'OrderPaid', payload: JSON.stringify(e) }).execute(); })` · Source B8.

**PAT-SAGA** — Saga: a business transaction that crosses services with their own databases, with no 2PC, as a sequence of local transactions with compensations (B8); the smell is one operation that needs consistency between two separately deployed services. If everything lives in one database it is a transaction. Verified costs: compensations to design by hand, **no isolation** (anomalies between concurrent sagas) and hard countermeasures (B8). Orchestration against choreography: choose orchestration when there are more than two or three steps [NV: a common criterion, not on the page]. Instead: do not split the service (ARQ-10); a local transaction. · How J · criterion D6 · Check: do the steps live in different databases? each step has its compensation and its test; the saga's states are persisted. DB-OWN-03; ERR-JOB-* · Source B8, B7 [NV body].

**PAT-IDEMPOTENT-RECEIVER** — Idempotent Receiver / Consumer: the receiver can get the same message more than once even if it is sent once (B7); delivery is at-least-once (B8); any queue consumer, webhook or retryable job that produces effects. It is never omitted where there is a retry; what is chosen is **how**: if the operation is naturally idempotent (`UPSERT`, “set state = X”) no deduplication table is needed (B7: define the message's semantics to be idempotent). · How T · criterion E4 · Check: a test of double delivery with the same id gives a single effect. TS `INSERT INTO processed_messages (subscriber, message_id) …` in the same transaction as the effect; a primary-key violation means a duplicate and is ignored (B8). DB-TX-04 and ERR-JOB-01 are not repeated · Source B7, B8.

**PAT-CQRS** — CQRS, when not: separate models to write and to read when reads need another shape or scale (B3, B8); the smell is screen queries that demand joins between services with their own databases, or a domain model deformed to serve views. Fowler: “for most systems it adds risky complexity”; only in parts of the system (a bounded context), never the whole (B3). Costs: more pieces, duplication, **replica lag** (eventual consistency in what the user just wrote) (B8). Separating `CommandHandler`/`QueryHandler` over **the same database and the same model** is not CQRS, it is ceremony. Instead: specific read queries (an SQL view, a direct query with a projection) next to the write model; a materialized view. · How C+J · criterion D6 · Check: [tried] `rg -n "(Command|Query)(Handler|Bus)\b" src/`; are there two stores or two models of truth? does the card tolerate stale reads? ARQ-10 · Source B3, B8, B11.

**PAT-EVENT-SOURCING** — Event Sourcing, when not: store the sequence of events as the source of truth and rebuild the state (B8); the smell is an explicit requirement of full audit with temporal reconstruction (“how was the account on 3 March”), or of publishing events reliably in an event-oriented system. Almost never otherwise. Verified costs: learning curve, a store hard to query, it **demands CQRS** (B8); replays against external systems, code changes and bitemporality are complicated; retrofitting is very hard; “just an event log is a small gain” because history can be kept in other ways (B3). Instead: an audit/history table next to the current state; outbox to publish. · How J · criterion D6 · Check: does the requirement ask to rebuild past states? If it only asks “who changed what”, an audit table. DB-ENG-01 (boring technology) · Source B3, B8.

## 5. Functional

**PAT-IMMUTABILITY** — Immutability: aliasing bugs (someone mutates a shared object and something changes far away) (B3) and change detection in UI by reference; the smell is a received object that gets modified (`props.items.push`), global mutable state, values that “change by themselves”. Not for copying large structures in a hot loop; **local** mutation inside a function (an array built and returned) is harmless. Instead: `readonly`, `Readonly<T>`, `as const`; spread for copies; `structuredClone` when a deep copy is really needed (ladder 2). · How C · criterion none · Check: ``rg -n "props\.\w+\.(push|splice|sort)\(|props\.\w+\s*=" src/`` returns 0; TS `readonly` in domain types; ESLint immutability rules [NV: plugin not evaluated]. ARQ-13 (do not mutate what is received) · Source B3, B9, B18.

**PAT-PURE-FUNCTION** — Pure functions / functional core: logic that depends on clock, randomness, environment or I/O is hard to test and to reason about; the smell is `Date.now()`, `Math.random()`, `process.env` or `fetch` inside a business rule, tests that need fake timers or mocks to test a calculation. Do not force purity at the edge (controllers, adapters): the effects go there; do not invent IO monads in TS. Instead: pass the instant, the configuration or the data as parameters (rule 3). Evans: “Side-Effect-Free Functions”. · How C · criterion D6 · Check: [tried] ``rg -n "Date\.now\(|new Date\(\)|Math\.random\(|process\.env" src --glob '**/domain/**'`` returns 0 (C15). TS `export const overdue = (f: Invoice, today: Date) => f.due < today` and at the edge `overdue(f, new Date())`. TDD-03; D6 (the injected clock is not speculative generality) · Source B9.

**PAT-RESULT** — Result/Either: make visible in the type the expected errors the caller must decide; the smell is a `try/catch` in each caller for normal business cases, domain errors that get lost because nobody knows they are thrown. Not for bugs and unexpected operational failures (they stay as exceptions); no mixing two styles in the same repo. **Already decided in `reference/errors.md` ERR-DES-06**: Result only for domain errors the caller decides; if the repo already chose a style, follow it. Instead: an own discriminated union (`{ ok: true, value } | { ok: false, error }`) before a dependency; neverthrow only if it is already there or the team adopts it with its lint (B21). · How C · criterion K11 · Check: `rg -n "neverthrow|Result<" src/` and ``rg -n "throw new \w*Error" src/**/domain/`` give a single style for domain errors; with neverthrow, `eslint-plugin-neverthrow` (B21). ERR-TAX-02 · Source B21.

**PAT-PIPELINE** — Pipelines / function composition: a transformation in clear stages (parse → validate → normalize → compute → format); the smell is a long function that mixes phases (Long Method) or temporary variables reused for different things; Fowler's **Split Phase** (B4). Not a generic `pipe(...)` nor a composition library for three calls, nor unreadable `.map().filter().reduce()` chains. Instead: named functions called in sequence with intermediate variables that say what they are; `node:stream` `pipeline` for I/O streams (ERR-CAP-10). · How J · criterion none · Check: does each stage have a name and can it be tested alone? K3 (cognitive complexity). TS `const rows = parseCsv(text); const valid = rows.filter(isValidRow); return summarize(valid.map(normalize));` · Source B4.

## 6. Front

**PAT-FRONT-STATE** — UI state: one owner, derived values and a single status; the smell is props copied into local state, derivable state stored, contradictory booleans, a `useEffect` that syncs state with state (B18). Not a global store for state one component or a subtree uses, nor for server data (use the data cache the repo already has). Instead: local state → lift it to the common ancestor → context → store, in that order. `reference/architecture.md` ARQ-13 is not repeated: the five criteria of B18 are added. · How C+J · criterion D13 · Check: ``rg -n -U "useEffect\(\(\) => \{\s*set\w+\(" src/`` (an effect that only copies state) and review each; are there two booleans that cannot be true together? TS `const [status, setStatus] = useState<'typing' | 'sending' | 'sent'>('typing'); const fullName = `${first} ${last}`;` (derived: computed, not stored) · Source B18.

**PAT-COMPOSITION** — Composition over inheritance: reuse behavior without coupling to a hierarchy; the smell is `extends` of components or service classes to “share code”, Refused Bequest, Parallel Inheritance Hierarchies (B6). Inheritance YES when the framework demands it (`HTMLElement` in custom elements, `Error` for typed errors) or a real, small hierarchy of types. Instead: `children`/`slot`, render props, hooks/composables, module functions (B18). · How C · criterion none · Check: [tried] ``rg -n --pcre2 "class \w+ extends (?!HTMLElement|Error|\w*Error\b)\w+" src/`` and review each. GoF p. 20 · Source B1, B4, B18.

**PAT-MODULE** — Module: encapsulate and expose only an interface; the smell is IIFEs, namespaces or static classes used as a container of functions. It is never needed as a pattern in TS: ES modules **are** the pattern (B12: “just export the names”). A class with only `static` methods is a module in disguise. · How C · criterion none · Check: classes with all their members `static` (`rg -n "^\s*(public\s+)?static " src/` grouped by file) become module functions. `rules/architecture.md` §Module boundaries; ARQ-04 · Source B12, B20.

**PAT-WEB-COMPONENT** — Web Components: a reusable component across frameworks or on pages with no framework, encapsulated (B19); the smell is the same widget in apps with different stacks, or a design system that several frameworks must consume. Inside a single-framework app a framework component is simpler (integrated state, SSR and forms) [NV: forms integration and SSR of custom elements not evaluated here]. · How J · criterion none · Check: ARQ-14 (an API by attributes/properties and `CustomEvent`; nobody enters another's `shadowRoot`) · Source B19.

## 7. Resilience

Retry with backoff and jitter, retry budget, circuit breaker, bulkhead, timeout, fallback, degradation and early rejection are in `reference/errors.md` ERR-RES-01 to ERR-RES-10, and the DLQ in ERR-JOB-02/03. The only thing added from patterns: they are implemented **once, in the adapter/gateway** of each dependency (PAT-ADAPTER, PAT-GATEWAY) or with the library the repo already has (ladder 4), never as decorators stacked in several layers (ERR-RES-03).

## Do I need a pattern here?

0. What concrete force does it solve? Write it in one line, with the file or the requirement where it is. If you cannot write it: NO, direct code (Yagni: the cost of carrying it, B3).
1. Does the repo already solve it (an existing pattern, helper, module)? Reuse it (ladder 1).
2. Does the language bring it (a first-class function, a module, a generator, a discriminated union plus `switch`, destructuring with defaults, `??=`)? Use it (ladder 2; Norvig, B12).
3. Does the platform/framework bring it (EventTarget, middleware, the database transaction, an ORM with a unit of work, `children`/`slot`, `useReducer`)? Use it (ladder 3).
4. Does a dependency that is already there cover it? Use it (ladder 4).
5. Is the force present today in 2 or more real places, or in 1 place plus a written requirement of variation (another provider, another customer, a plugin)? If not: NO, duplicate or write it inline (Metz, B14; “two uses are not a pattern”).
6. What is the smallest form? function > object literal > class > interface + classes. Take the smallest that absorbs the force.
7. Is there a second consumer of the abstraction (another implementation, or a test fake)? If not, no interface (“no interface to satisfy DIP”; the D6 exception is the clock/storage).
8. You arrived by refactoring, with green tests before and after, in a commit of its own (Kerievsky, B5; Beck, B15). If after a month the abstraction accumulates parameters and conditionals: inline it and look again (Metz, B14).

Exceptions where the pattern **is not discussed** because it is a requirement of the method or of correctness: idempotent consumers where there is a retry (PAT-IDEMPOTENT-RECEIVER), outbox where there is a database plus a broker (PAT-OUTBOX), an adapter for SDKs that embody a decision that changes (ARQ-07), a value object for money (PAT-MONEY). As in the ladder, what the method asks explicitly is not “extra”.

**Patterns an AI agent tends to put in without need.** The frequency is the study's judgment, not a measured figure; the kit measured in its runs that agents overdesign (“What not to do” exists for that) and that agent code leaves unused symbols (K5).

The gate's `overdesign` check (`gate-checks.mjs`) fails what the card adds of A1 (one implementation, no fake in the repo), A3 (a method that forwards with the same arguments) and A11 (a folder with one tiny file; empty layer folders of a slice are expected, not flagged), and reports the same in code that was already there; the plan asks `why-layer:` for the rest.

## The detectors (mechanical, criteria D1, D4, D6 and K6)

They are informative: the result is read by whoever closes the card, it does not block. They were run over a sample tree (`/tmp/pat-sample`, deleted afterwards) with a positive and a negative case per command and gave only the positives. They need `rg` with `--pcre2` for the one over forwarding methods. Each finding is looked at, not deleted blindly. They are lines of the gate; the commands by stack are in `stacks/node-ts.md`.

**C12 — Interfaces with at most 1 implementation and no fake in tests** [tried]:

```bash
for i in $(rg -o --no-filename -N "^export interface (\w+)" -r '$1' src | sort -u); do
  impl=$(rg -c "implements[^{]*\b$i\b" src --glob '!*.test.ts' | awk -F: '{s+=$2} END{print s+0}')
  fake=$(rg -c ":\s*$i\b|implements[^{]*\b$i\b" src --glob '*.test.ts' --glob '*.spec.ts' | awk -F: '{s+=$2} END{print s+0}')
  [ "$impl" -le 1 ] && [ "$fake" -eq 0 ] && echo "$i impl=$impl fakes=$fake"
done
```

Limit: it does not see implementations by a typed object literal (`const x: Port = {…}`) outside tests nor tests in another folder; adjust the globs. A `type X = {…}` used as a port does not enter (change the pattern to `^export (interface|type) (\w+)`).

**C13 — Abstract classes with at most 1 subclass** [tried]:

```bash
for c in $(rg -o --no-filename -N "abstract class (\w+)" -r '$1' src | sort -u); do
  n=$(rg -c "extends\s+$c\b" src | awk -F: '{s+=$2} END{print s+0}'); [ "$n" -le 1 ] && echo "$c subclasses=$n"
done
```

**C14 — Methods that only forward to the same-named method of a collaborator** (Middle Man, D4) [tried]:

```bash
rg -U -n --pcre2 "(?:async\s+)?(\w+)\s*\(([^)]*)\)\s*(?::[^{]+)?\{\s*return\s+(?:await\s+)?this\.\w+\.\1\([^)]*\);?\s*\}" src
```

It does not see forwarding under another name; for that, judgment.

**C15 — Impurity in the domain** [tried]: ``rg -n "Date\.now\(|new Date\(\)|Math\.random\(|process\.env" src --glob '**/domain/**'``

**C16 — Name patterns** (an alert, not a verdict) [tried on the sample]: ``rg -n "class \w+(Factory|Builder|Strategy|Mediator|UnitOfWork|IdentityMap|Dto)\b|(Command|Query)(Handler|Bus)\b|static getInstance|new EventEmitter\(" src/``

Tools that cover part without scripts [NV: not run this session]: `knip` and `ts-prune` for unused exports (K5); `jscpd` for duplication (K4, which `verify.mjs` runs in every grade; and to measure whether the “abstraction” removed anything); `dependency-cruiser` for deep imports (ARQ-04).

**Questions of judgment for the reviewer.** (1) What force does it solve, and where is it written (file or requirement)? No answer → surplus. (2) If I inline it, how many lines are duplicated and in how many places? At most 1 place → surplus. (3) How many implementations, subclasses, subscribers or variants does it have **today**? 1 → surplus unless a test fake or a written requirement of a second one. (4) Is the interface smaller than what it hides (D4)? If each method forwards, it is Middle Man. (5) How many files does a typical change touch (adding a field, a variant)? If the pattern raised it, it is costing (measured by the kit: 8 files against 4, `rules/architecture.md` rule 2). (6) Has it grown with parameters and conditionals since it was created? → the wrong abstraction (B14). (7) Does the language, the platform or a present dependency already do it (ladder 2–4)?
